## Findings (from the reviewer, all confirmed in source at `fa5177e`)

1. **Malformed SHA-256 bypasses integrity validation.** `manifest.files.*.sha256`
   (media_validate.py ~685) and the checksums sidecar (~879) compare only when
   `_LOWER_HEX_64` (`\A…\Z`) matches; a value of 64 hex chars plus a trailing
   `\n` passes the schema pattern `^[0-9a-f]{64}$` (Python `$` matches before a
   final newline) and then silently skips the comparison. Same silent skip for
   missing/malformed `bytes`.
2. **Active segments can exceed 3600 frames.** The frame `seq` maximum
   suppression (media_validate.py:74-77) assumes the manifest `frame_count`
   bound enforces the ceiling, but active records have no `frame_count` and
   `_walk_index` has no independent cap.
3. **Required JSON bodies can be omitted.** Schema validation runs only when
   `_load_body()` returns bytes (api_validate.py:161); a header-only vector can
   claim `PairResponse` etc. and pass. The final empty-vector check (279-291)
   is request-side and headers-free only.
4. **The 16 KiB control-request limit is applied to responses too**
   (api_validate.py:162) — a valid 100-item backend clips page would be
   falsely rejected. `MAX_CONTROL_BODY_BYTES` in bounds.py is documented as a
   request bound.
5. **Non-JSON numeric literals accepted.** `json.loads` (api_validate.py:174)
   defaults to accepting `NaN`/`Infinity`; `"progress": NaN` passes the type
   check and escapes both range comparisons. Fixture writing uses the default
   `allow_nan=True`.
6. **Header validation disagrees with the selected operation.**
   `_rule_content_type` (api_validate.py:803) checks a global set, so a preview
   response with `Content-Type: application/json` passes; and
   `Cache-Control: no-store` — documented for preview in device-v1.yaml
   (~224-227, ~661 `const: no-store`; interfaces.md:106) — has no rule in
   `HEADER_RULES`, so a conforming preview response is rejected.
7. **Clock uncertainty lacks the shared 2^53−1 ceiling.** media section 2
   requires shared integers ≤ 2^53−1, but `uncertainty_ms` carries only a
   minimum in manifest.schema.json:190, active-record.schema.json:111, and
   both OpenAPI mirrors (device-v1.yaml ~1442, backend-v1.yaml ~1809), and
   `_clock_violations` (media_validate.py:809) tests only negativity.
8. **Two required refusals are missing from the frozen API.** `device.pair`
   omits 403 (closed physical claim window; interfaces §1-2) and
   `backend.patch_upload_file` omits 410 (expired upload; interfaces §8) in
   api_model.py; the YAMLs and golden fixtures lack both.
9. **HEAD fixtures carry forbidden bodies.** The three committed
   `head_upload_file-response-401/404/410` vectors ship JSON error envelopes;
   RFC 9110 §9.3.2 forbids any HEAD response content, including errors.

## Orchestrator rulings (authoritative design decisions)

**R1 (findings 1).** Reject malformed integrity fields explicitly; never skip.
- Both media schemas and their OpenAPI mirrors: where `sha256` is declared,
  add `"minLength": 64, "maxLength": 64` alongside the existing `pattern`
  (portable across regex dialects; catches the trailing-`\n` hole at the
  schema level). Keep every existing `pattern` string unchanged.
- Dedicated checks (`manifest.files` block and `_validate_checksums`) must
  report instead of skip: a present-but-malformed `sha256` (a string failing
  `_LOWER_HEX_64`) and a missing/non-integer `bytes` each produce a finding —
  `MANIFEST_HASH_MISMATCH`/`MANIFEST_SIZE_MISMATCH` for manifest file entries,
  `CHECKSUMS_SCHEMA` for sidecar entries (message names the malformed value
  shape). Exact committed-code sets follow what the validator actually emits
  (schema-level reports may add a code); commit the observed set.
- No new error codes anywhere this round; the registry in errors.py is frozen.

**R2 (finding 2).** In `_walk_index`, refuse any record at position
`>= MAX_FRAMES_PER_CLIP` (the 3,601st, zero-based record 3600) with the
existing `FRAME_COUNT_MISMATCH` ("a clip retains at most 3,600 frames") and
stop the walk. One gate covers both finalized and active paths. Update the
seq-suppression comment (lines 74-77) to name the walk gate. Tests must cover
finalized AND active segments at 3,600 (valid) and 3,601 (flagged); commit one
active invalid vector via fixture_spec (unit tests may cover the rest).

**R3 (finding 3).** Check body presence against operation, direction, and
status before validating contents, inside `validate_vector`:
- request with `operation.request_schema` set and no body file → one
  `API_SCHEMA` finding (naming the required body); response whose status maps
  to a non-None `response_schemas` entry and no body → same; response whose
  status is a documented ≥400 (shared envelope) and no body → same. Skip these
  when the method is HEAD (see R9) or status is 204.
- A body where the contract allows none (HEAD response; 204 response) →
  `FIXTURE_INDEX_INVALID` naming the forbidden file.
- Documented non-JSON bodies (`response_schemas[status] is None`, e.g.
  preview/clip-file/derivative) keep their current silent path.
- The empty-vector check at 279-291 stays as is.
New invalid vectors: header-only `device.pair` request (sidecar with
`Content-Type: application/json` so it is not the empty-vector case) and
header-only `device.pair` 201 response; each declares its observed code set.

**R4 (finding 4).** The size gate at api_validate.py:162 applies only when
`direction == "request"`; keep `operation.body_bound_bytes or
MAX_CONTROL_BODY_BYTES` for requests (32 KiB upload-init exception intact).
Responses get no size gate (their published limits live elsewhere:
manifest-binding rules, content-length header rules). Update any message text
that says "request limit" only if it becomes inaccurate. Regression: commit a
VALID backend clips-page 200 response with 100 items exceeding 16 KiB
(generate it through fixture_spec; verify with the validator that it now
passes and that reverting the direction gate flags `API_BODY_TOO_LARGE`).

**R5 (finding 5).** Strict wire JSON: parse fixture bodies with a
`parse_constant` hook that raises on `NaN`/`Infinity`/`-Infinity`, so the
existing `API_SCHEMA` "body is not JSON" path fires. Every fixture-writing
`json.dumps` in generate_fixtures.py / fixture_spec.py gains
`allow_nan=False`. Commit one invalid vector whose raw body contains literal
`"progress": NaN` (job response) declaring `API_SCHEMA`; add a raw-wire unit
test. If the generator has no raw-body mechanism, add a narrow one (e.g. a
vector field carrying exact bytes) so regeneration stays byte-identical.

**R6 (finding 6).** Judge `Content-Type` and documented optional headers
against the selected operation and status:
- Extend `Operation` with the media types that operation may carry (JSON
  operations: `application/json`; `device.get_preview` 200: the documented
  `multipart/x-mixed-replace; boundary=frame`; file download/HEAD operations:
  `application/octet-stream`; PATCH chunk upload request: per interfaces —
  verify in docs/specs/interfaces.md and the YAMLs and encode exactly what is
  documented, nothing more). `_rule_content_type` flags values outside the
  operation's set with `HEADER_INVALID`, keeping the global
  `DOCUMENTED_CONTENT_TYPES` as the cross-contract vocabulary where it still
  earns its place.
- Add a `cache-control` rule to `HEADER_RULES` accepting `no-store` only where
  the spec/YAML documents it (preview response) and flagging it elsewhere;
  verify in the YAMLs whether other operations document it before allowing.
- Align the operation table with what device-v1.yaml documents for preview
  (if the YAML requires `Cache-Control: no-store` on the preview 200, add it
  to `required_response_headers` and to the generated preview headers
  sidecars; record the byte-delta honestly — round-1 preview vectors are not
  protected artifacts).
- Vectors: invalid preview 200 with `Content-Type: application/json`
  (`HEADER_INVALID`); valid preview 200 carrying `Cache-Control: no-store`
  (zero findings); invalid JSON response (e.g. pair 201) with
  `Cache-Control: no-store` (`HEADER_INVALID`).

**R7 (finding 7).** Add `"maximum": 9007199254740991` to `uncertainty_ms` in
manifest.schema.json, active-record.schema.json, AND both OpenAPI clock
mirrors, keeping media schemas and mirrors identical (openapi_check's
tie-outs must stay green). `_clock_violations` gains the ceiling beside the
existing negativity test (same finding site/code as the negative case or its
documented sibling — follow the established dedicated-code pattern; if a
suppression pair is needed so the schema keyword is not double-reported, add
it to the clock table the way `(start_utc, "pattern")` is handled and ensure a
committed vector exercises the dedicated code, per test_error_codes). Tests:
boundary 2^53−1 valid, 2^53 flagged. Commit one invalid vector
(uncertainty 9007199254740992) declaring the observed codes.

**R8 (finding 8).** Add `403: ("FORBIDDEN",)` to `device.pair` and
`410: ("EXPIRED",)` to `backend.patch_upload_file` in api_model.py; add both
statuses with the shared error envelope to `contracts/device-v1.yaml` (/pair)
and `contracts/backend-v1.yaml` (PATCH /uploads/{id}/files/{name}) matching
each file's existing error-response style; verify against docs/specs
interfaces §1-2 and §8 first. Commit golden valid vectors for both (naming
pattern: existing `*_response-403-forbidden` / `*_response-410-expired`
siblings).

**R9 (finding 9).** HEAD responses never carry content:
- Model: `headUploadFile` error responses are status-only outcomes. If
  backend-v1.yaml gives them JSON content, remove it to match RFC 9110
  §9.3.2 (record the delta).
- Validator: in the response path, HEAD + named body file → `FIXTURE_INDEX_INVALID`
  (R3); `_validate_error_vector` is never reached for HEAD (status-only), so
  the required-envelope walk must not demand a body for HEAD error statuses.
- Generator: re-cut the three committed `head_upload_file-response-401/404/410`
  vectors as body-less (status-only, or headers per what the contract
  documents for those statuses); rewrite their `invariant` text to say the
  refusal is carried by status alone on a HEAD. Update fixtures.json via the
  generator only.
- Commit one invalid vector: `head_upload_file` 410 response WITH a JSON
  error body, declaring the observed code set (expected: `FIXTURE_INDEX_INVALID`).
