## Background (verified in source at `fd392fd`)

- `_rule_range` (tools/contracts/api_validate.py) flags unsupported syntax and
  reversed ordering only for `context.status in (200, 206)`. A `direction ==
  "request"` vector has `status: null` (see `device/valid/
  clip-file-request-with-lease`, headers `{"Range":"bytes=0-1023",
  "X-Clip-Lease":...}`), so request-side `bytes=10`, multipart, suffix or
  reversed ranges produce **no finding**. The RFC-precondition excuse is a
  response-side property only: a *request* carrying an unsupported range form
  is itself outside interfaces §4 ("Support single `Range: bytes=start-end` or
  `bytes=start-` only"), and reversed endpoints can never be served.
- `load_media_schemas` (tools/contracts/openapi_check.py ~56-97): after
  `load_json`, a non-Mapping root reaches `check_metaschema`/`check_local_refs`
  and then `document.get("$schema")` → `AttributeError` → CLI exit 2. Roots:
  `null` (metaschema failure recorded, crash before `continue`), `[]` (valid
  metaschema array schema, crash at `.get`), `true` (boolean schema, same), and
  any scalar/string root.
- `_walk_index` (tools/contracts/media_validate.py ~459-468) gates on
  `type(record[name]) is int` for `offset`/`size`, refusing wire-valid JSON
  integers written as `0.0` or exponent notation (`1e2`) with `FRAME_SCHEMA`.
  The published schema (`type: integer`) and this package's own `_is_int`
  accept them; Python slicing needs must not narrow the contract.

## Fix 1 — request-side Range validation (`api_validate.py`)

Add a **request-direction branch at the top of `_rule_range`**, before any
status inspection:

- `context.direction == "request"`:
  - `_SINGLE_RANGE` does not match (multipart, suffix, `bytes=10`, junk) →
    `RANGE_MULTI_NOT_ALLOWED` ("the contract makes only `bytes=start-end` and
    `bytes=start-` requests").
  - matched with `end < start` → `RANGE_MULTI_NOT_ALLOWED` (unsatisfiable
    ordering may never be requested).
  - otherwise silent (EOF is unknowable in a request).
- Response branch: **unchanged** (gate silence from Ruling 1 is deliberate).
- Update the decision-table comment: add the request row and state why the
  precondition-echo reasoning does not apply to requests.

## Fix 2 — non-object schema roots crash (`openapi_check.py:76` + adjacency)

  violation naming the file and the offending root type, then `continue`
  (document is never stored in `schemas`). This must precede
  `check_metaschema`/`check_local_refs` and every `.get`.

Adjacent same-class hole (Orchestrator-authorized): in `validate.py`'s OpenAPI

## Fix 3 — byte-position notation (`media_validate.py:462`)

Replace the exact-`type() is int` gate: accept `offset`/`size` per `_is_int`
(JSON integer semantics incl. integral floats and exponent notation — the
public behavior the schema publishes), then **convert to `int` before any
arithmetic that indexes bytes**: `offset, size = int(offset), int(size)`
immediately after acceptance, before `offset + size > len(payload)` and the
slice. Non-integral values (float `5.5`, string, bool, missing) keep a
walk-stopping `FRAME_SCHEMA` violation (reword the message: values must be
integral JSON numbers per the schema). Keep the finding site and code stable
so committed vectors' declared codes don't move.

Tests (`tests/test_media_contract.py`):
- Update `test_a_float_byte_position_is_a_finding_not_a_crash`: non-integral
  float/string/bool → `FRAME_SCHEMA` as today.
- New positive tests using the existing synthetic-media pattern: a clip whose
  first index line spells `"offset":0.0` and/or `"size":512.0` (and one
  exponent-notation `1e2`-style size where the payload allows) validates with
  **zero findings** — same frame content, CRC and JPEG checks as the integer
  spelling; and the walk's continuity/`previous_end` bookkeeping still accepts
  the following record's integer offset.

No committed corpus change is expected for fix 3 (existing valid vectors are
plain integers); if you instead commit a notation vector through the
generator, keep counts honest.
