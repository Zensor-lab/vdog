## Fix 1 — integral floats bypass media bounds (`tools/contracts/media_validate.py:857`)

Root cause: `_is_int()` rejects `float`, so `duration_us: 120000001.0` skips the
dedicated `DURATION_TOO_LONG`/`DURATION_LE_FINAL_T_US` check at line 615, while
the schema `maximum` report for that property is suppressed via
`MANIFEST_DEDICATED_RULES` → nothing is reported. Same bypass for profile
bounds (`_profile_bound_violations`), frame `size`/`t_us`, `frame_count`,
declared `bytes`, dimensions, `uncertainty_ms`.

Fix: accept integral numbers only — `int` (excluding `bool`) or `float` with
`value.is_integer()` (this rejects NaN/inf). One helper change covers every
call site; keep the docstring accurate about JSON semantics.

Regression vectors (invalid media clip vectors, new `_corrupt_*` byte-level
mutators writing raw JSON text so the *notation* is what is tested):

1. `duration_us: 120000001.0` → expect exactly `DURATION_TOO_LONG`.
2. `duration_us: 1.20000001e8` (exponent notation text) → `DURATION_TOO_LONG`.
3. `profile.width: 1601.0` → `DIMENSIONS_EXCEEDED`.
4. `profile.nominal_fps: 31.0` → `NOMINAL_FPS_INVALID`.

(Each also observes no extra codes; e.g. `120000001.0` is still `type: integer`
so no schema `type` finding appears.)

## Fix 5 — Range rule confuses syntax with satisfiability (`tools/contracts/api_validate.py:37,515`)

Current `_SINGLE_RANGE = bytes=[0-9]+(-[0-9]*)?` accepts malformed `bytes=10`,
and every 416 for a "supported" range is flagged, even a beyond-EOF start.
Implement exactly this decision table (documented in the module comments, citing
interfaces §4 and RFC 9110 semantics):

- `_SINGLE_RANGE = re.compile(r"\Abytes=([0-9]+)-([0-9]*)\Z")` — the hyphen is
  mandatory. Anything else (multipart, suffix, `bytes=10`, junk) is **unsupported
  syntax**: 416 is required (no violation), any other status is
  `RANGE_MULTI_NOT_ALLOWED`.
- Supported syntax with `end < start` (**endpoint ordering** unsatisfiable):
  416 acceptable; 200/206 is `RANGE_MULTI_NOT_ALLOWED` (message: unsatisfiable
  ordering must be refused with 416).
- Supported, correctly ordered (including `bytes=start-`): 416 is acceptable
  **only when provably beyond EOF**: the response carries
  `Content-Range: bytes */<total>` (new `_STAR_CONTENT_RANGE` regex) and
  `start >= total`. Otherwise (absent header, or `start < total`) the 416 is
  `RANGE_MULTI_NOT_ALLOWED`.
- `_rule_content_range`: accept the star form **only** for status 416 (reject
  `bytes */N` on 200/206, reject granted form on 416; Content-Length equality
  applies only to the granted form). Skip it for the star form's total ≤ 0
  (total ≥ 1 required).
- `openapi_check._EXPECTED_HEADER_SCHEMAS["ContentRange"]` and
  `contracts/device-v1.yaml` `components/headers/ContentRange` pattern must
  allow the star form: `^bytes ([0-9]+-[0-9]+|\*)/[0-9]+$`. The 416 response
  docs do not need the header listed (still optional in the contract).

New vectors (device/get_clip_file, category `range`; existing
`clip-file-response-416-multi-range` and invalid
`clip-file-response-416-without-multi-range` must keep passing unchanged):

1. **valid** `clip-file-response-416-hyphenless`: `Range: bytes=10`, 416,
   `RANGE_INVALID` envelope → no findings (unsupported syntax refused).
2. **invalid** `clip-file-response-206-hyphenless`: same malformed Range served
   with the standard 206 header set → exactly `RANGE_MULTI_NOT_ALLOWED`.
3. **valid** `clip-file-response-416-beyond-eof`: `Range:
   bytes=999999999-`, `Content-Range: bytes */<baseline_payload_bytes>`, 416
   envelope → no findings.
4. **valid** `clip-file-response-416-reversed`: `Range: bytes=200-100`, 416
   envelope → no findings.
5. **invalid** `clip-file-response-206-reversed`: `Range: bytes=200-100` with
   the standard valid 206 headers → exactly `RANGE_MULTI_NOT_ALLOWED`.

Unit-test the table directly in `tests/test_api_contract.py` (helper-built
contexts) in addition to the vectors, including the "416 + supported range +
Content-Range proves satisfiable" → flagged case.
