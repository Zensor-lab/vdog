# Stage 0.9 firmware CI and installation release plan

Status: **PLAN READY — implementation not started**, 2026-11-20.
Baseline inspected: `b0cb29bd1690f94eb9b72a0ceb9697681bf9f374` on
`opencode/0.2-toolchains`. This assignment adds the release delivery work after
the qualified 0.2 bootstrap; it does not claim that workflows or installers
already exist. Follow [AGENTS.md](../../AGENTS.md) for implementation worktrees,
specialist review, independent checks and delivery.

## 1. Goal and acceptance contract

Every pull request builds the pinned XIAO ESP32S3 Sense firmware, runs the
implemented host checks and produces a downloadable installation bundle whose
name includes the PR's latest head commit hash. Every successful `main` update
rebuilds/tests that exact commit, creates an immutable Git tag at it and publishes
a GitHub Release containing everything needed to install the prebuilt firmware.
PR builds never create tags or Releases.

The user explicitly requested PR builds, automatic releases/tags after merging
to `main`, installation instructions/scripts and commit hashes in PR build names.
The following conventions resolve routine implementation choices:

| ID | Required behavior |
| --- | --- |
| CI-01 | Run firmware CI on every PR opening/reopening/head update, including documentation-only PRs and drafts; do not add path filters that skip builds |
| CI-02 | PR identity is `github.event.pull_request.head.sha`; build that exact head SHA, not a mutable branch name or an assumed PR merge SHA |
| CI-03 | Use `push` to `main` as the post-merge trigger; build/test/package `github.sha` again, independently of PR artifacts |
| CI-04 | Create a source-addressed tag only after the main build, host tests and package checks pass; tag and release resolve to that exact main SHA |
| CI-05 | Publish a complete, validated install bundle, guide, source identity, checksums, flash manifest and pinned installer dependencies |
| CI-06 | Use the same package/validation/installer code for PR and main builds; credentials and publish rights exist only in the trusted main publish job |
| CI-07 | Refuse incomplete, mismatched or corrupted packages and conflicting existing tags; retries never overwrite an already published release |
| CI-08 | Installation is explicit and device-specific; no automatic chip selection followed by flashing, full-chip erase, eFuse writes or security bypass |
| CI-09 | Current bootstrap builds are clearly marked prototype/pre-release and BUILD/HOST-only; no recording or hardware-support claim is inferred |
| CI-10 | Preserve ordinary version semantics; Git source identity is separate metadata and must appear in bundle names, manifest and startup build ID |

`push: branches: [main]` also covers direct pushes. Treat those consistently;
require PRs through branch protection if the repository owner wants merge-only
development. Do not use `pull_request: closed` as a substitute for testing the
actual merged source. A failed build publishes neither a new tag nor release.

## 2. Existing inputs and limits

- [Toolchain](../toolchain.md): PlatformIO Core 6.2.0, Python 3.12, official
  `platformio/espressif32@8.0.0`, ESP-IDF 6.1.0, exact package pins and tracked
  `firmware/dependencies.lock`; camera component 2.1.9 links in the bootstrap.
- `firmware/platformio.ini`: environments `vdog_xiao_sense_proto` and `native`.
- `firmware/sdkconfig.defaults`: 8MB flash, octal PSRAM, USB console and rollback.
- `firmware/partitions/vdog_8mb_two_ota.csv`: application slot A at `0x20000`,
  slot B at `0x320000`, each `0x300000` bytes. Firmware currently reports a
  version and links the camera driver; camera/SD/Wi-Fi are not initialized.
- [Current installation guide](../installation.md): source-build/PlatformIO USB
  instructions. Retain that developer route and add a distinct prebuilt route.
- The inspected generated `flasher_args.json` gives bootloader `0x0`, partition
  table `0x8000`, initial OTA data `0xf000` and application `0x20000`, with DIO,
  8MB and 80m upload settings. These values are observations, not constants to
  duplicate permanently in an installer.
- Generated IDF paths currently differ from actual PlatformIO outputs:
  `bootloader/bootloader.bin`, `partition_table/partition-table.bin` and
  `vdog_firmware.bin` are absent locally, while `bootloader.bin`, `partitions.bin`
  and `firmware.bin` exist. The packaging step must reconcile the pinned builder's
  resolved outputs, not blindly copy those JSON paths or guess by basename.

This package depends on 0.2, not on completed recording, API/media fixtures,
Flutter/backend or device OTA. It defines its own release manifest/fixtures.
Integrate future 0.6 checks when those tools actually exist. Physical flashing
and stable product qualification remain later DEVICE gates.

## 3. Build names, tags and provenance

Validate commit inputs as full Git object IDs and use the first 12 hexadecimal
characters only for human-readable names. Preserve the full SHA in metadata.
Do not incorporate untrusted PR titles or branch text into shell commands/paths.

| Context | Identity and name |
| --- | --- |
| PR source | Full `pull_request.head.sha`, explicitly checked out; record PR base SHA separately |
| PR display/run name | `Firmware PR #<number> @ <full-head-sha>` |
| PR build ID | `pr-<number>-<head-sha12>` |
| PR artifact ZIP | `vdog-xiao-sense-pr-<number>-<head-sha12>-run<run_id>-a<attempt>.zip` |
| Main source | Full triggering `github.sha`, explicitly checked out; never resolve mutable `main` again for the build |
| Main build ID | `main-<main-sha12>` |
| Git tag | `firmware-main-<main-sha12>`, immutable, created at the full triggering main SHA |
| Release title | `vdog <source-version> — main <main-sha12>` |
| Release ZIP | `vdog-xiao-sense-main-<main-sha12>.zip` |

Stable required-check names are `firmware-build`, `firmware-host-tests` and
`firmware-package-tests`. Put variable hashes in run/artifact/build IDs, not in
required-check names, so branch protection does not need a new rule per commit.
Use the full event SHA in workflow `run-name`, which is evaluated before jobs;
derive the short SHA in the validated metadata step for build/artifact names.
Do not depend on a job output or unsupported substring expression in `run-name`.

PR `GITHUB_SHA` normally denotes a synthetic merge commit. Explicit head checkout
is required here so source and requested name agree. Merge-ref/`merge_group`
integration checks may be added separately; they must identify their different
source and must not replace the head artifact or publish releases.

This plan uses commit-based tags, not automatic SemVer increments. Keep source
version `0.2.0-proto` until separately changed in source; never silently bump it
because a docs PR merged. A 12-character tag collision or existing tag pointing
at a different full SHA is a hard conflict, not permission to move a tag.

## 4. Release and installation payload

One ZIP root contains the following required files. These are future outputs;
do not add empty placeholders or commit generated firmware to source control.

```text
vdog-xiao-sense-<build-id>/
  INSTALL.md
  RELEASE_NOTES.md
  VERSION.json
  manifest.json
  SHA256SUMS
  LICENSE
  THIRD_PARTY_NOTICES.md
  images/
    bootloader.bin
    partitions.bin
    ota_data_initial.bin
    firmware.bin
  flash/
    partitions.csv
    flash-layout.json
    flash_args
  install.py
  install.sh
  install.ps1
  requirements-installer.lock
```

Publish the ZIP, its external `.sha256`, and readable installation/release notes
as Release assets. Keep a build report/image-size map and ELF/map files as
separate debug artifacts where useful; they are not required for end-user
installation. The auto-generated GitHub source ZIP is not the installation ZIP.
Include required third-party attribution/license texts in the notices or a
bundled `licenses/` directory; resolve decision D-15 before public distribution.

`manifest.json` is a new `firmware-release-v1` contract, separate from recording
media/API v1. Required metadata includes product and exact supported hardware
class, target `esp32s3`, expected flash bytes, board/environment, firmware version,
full source SHA, PR head/base or main identity, build ID, tag (main only), run ID/
attempt, toolchain versions, partition-table hash, flash parameters, image file
roles/offsets/sizes/hashes, package format version and feature/evidence status.
Record `release_channel: prototype`, `hardware_verified: false`,
`recording_available: false` and `device_ota_available: false` for the present
bootstrap. Future releases update these only with appropriate evidence.

Every payload file is covered by size/SHA-256 entries; exclude `manifest.json`
and checksum files from self-referential manifest hashing. `SHA256SUMS` covers
the manifest and payload, excluding itself; the external ZIP digest covers the
complete archive. Validate paths, lengths, overlaps, flash bounds, partition
roles and application size. Checksums detect corruption; authenticity still
depends on obtaining the intended release from the trusted repository.

Never ship provisioning secrets, credentials, MAC inventories, private signing
keys, developer paths/caches or a prefilled NVS identity image. No generic
8MB padded merged image is required: padding can erase NVS/settings between
segments. Default installation uses the validated individual segments.

### Installer behavior

End users need a supported Python 3.12 runtime, the ZIP, a data-capable USB-C
cable and the correct XIAO ESP32S3 Sense. They do not need PlatformIO, ESP-IDF,
the compiler or a source checkout. Select/test exact Python patch and installer
dependency hashes during implementation. Pin esptool to the qualified 5.4.0
line/version from 0.2, with exact compatible transitive versions; verify the
distribution actually used. Do not silently use whichever esptool is installed.

`install.sh` and `install.ps1` create/reuse an isolated local installer environment
after explicit setup, install the locked dependencies and invoke the same Python
entry point. Never modify global Python or ship a copied virtualenv. First setup
needs network access; document that prerequisite. Fully offline Python/runtime
and wheel distribution is a separately scoped extension, not a claimed feature.

Proposed CLI contract:

| Command | Effect |
| --- | --- |
| `install.py check` | Validate package/manifests/hashes locally; no serial access |
| `install.py ports` | Enumerate ports; no flashing or automatic selection |
| `install.py plan --board seeed-xiao-esp32s3-sense` | Print validated segments/actions; no serial access |
| `install.py inspect --port <port>` | Explicit read-only chip/flash/security inspection; no flash/erase/eFuse action |
| `install.py install --port <port> --board seeed-xiao-esp32s3-sense` | Validate package and device, show changes and require confirmation before writing |
| `install.py install ... --dry-run` | Print the planned invocation without opening the serial port |
| `install.py install ... --confirm-replace` | Explicit noninteractive consent to replace the listed firmware ranges; never an erase/security bypass |

The installer requires an explicit port, checks `esp32s3` and expected 8MB flash,
and rejects incompatible security state/images. Chip ID/USB VID/PID cannot prove
that a board is a Sense: require the hardware-class acknowledgment and approved
unit/revision instructions. Do not use a generic `--force`, bypass flash-encryption
checks, burn eFuses, disable secure boot or auto-run a full-chip erase.

Initial mode is a **prototype factory/recovery segment install**, not OTA or a
guaranteed data-preserving upgrade. It writes the listed bootloader/partition/
OTA-data/application ranges, replaces the firmware and resets boot selection;
it may invalidate settings if a partition layout changes. A demonstrably blank,
unprovisioned board may use the explicit factory-install route after confirmation.
For an existing installation, require the qualified matching layout and an
unprovisioned development state; unreadable or unknown layouts are not assumed
blank. Paired/provisioned devices need a separately qualified preservation/
backup/migration route. Do not overwrite NVS, reserved data or the SD card by
default. An app-only USB mode is deferred until active-slot selection and
compatibility are implemented; writing blindly to `0x20000` can boot the old slot.

Guide both Windows `COM...` and macOS/Linux port selection, USB download-mode
BOOT/RESET recovery, changed ports, permissions, disconnected battery, integrity
checks and expected logs/build ID. Do not copy `.bin` files onto a USB drive.
The XIAO's onboard charger exists: unplug the pack before any USB service.

Current unsigned bootstrap images may be installed only on compatible development
boards. SHA checksums/Git tags do not make them signed OTA images. This package
must not change Stage 2 signature/rollback requirements or provisioning policy.

## 6. Detailed implementation work packages

### 0.9.1 Freeze release identity and manifest contract

- Inputs: this plan, source version functions, actual 0.2 partition/config and
  generated layout metadata. No dependency on media/API implementation 0.6.
- Define required types/enums/bounds, normalized paths, byte/hash coverage,
  source/channel/status fields and image roles in the release schema.
- Create small synthetic valid/invalid package fixtures, not private hardware
  records or copies of generated binaries committed as normal build output.
- Acceptance: inconsistent SHA/name/tag/source, path escape, overlap, oversized
  image and missing installation files fail deterministically. Record schema v1.

### 0.9.2 Export source identity and firmware build ID

- Depends: 0.9.1; bounded ESP32/Python integration.
- Derive head/main full SHA from validated CI event inputs and confirm checkout
  `HEAD` matches it. Record base SHA on PRs; reject a dirty/replaced main source.
- Generate ignored build metadata, log a separate build ID/source SHA at startup
  and include it in `VERSION.json`; preserve semantic version APIs/native tests.
- Acceptance: PR update changes the hash/name, main uses its merged/squashed SHA,
  and local builds have an explicit local/unpublished identity. No PR input is
  evaluated as shell code or arbitrary C preprocessor text.

### 0.9.3 Normalize real flash outputs and package images

- Depends: 0.9.1–2 and 0.2's clean build.
- Export the pinned PlatformIO builder's actual application and extra-image
  paths/offsets/upload parameters after a normal release build; no upload target.
- Cross-check generated IDF flash metadata, partition CSV/binary and resolved
  builder output. Handle the observed IDF/PlatformIO path differences explicitly
  by role; reject unknown/missing/conflicting output instead of globbing `.bin`.
- Package only the normal firmware image, never the embedded test runner left
  by `pio test`. Separate build directories or rebuild cleanly after test builds.
- Acceptance: current offset set is `0x0/0x8000/0xf000/0x20000`, 8MB/80m/DIO at
  the inspected baseline. Changed partitions regenerate metadata; hardcoded
  `0x10000` app or `0xe000` OTA assumptions fail tests. No stale output fallback.

### 0.9.4 Validate complete installation archives

- Depends: 0.9.3.
- Implement schema/hash/path/partition/file-size validation and safe archive
  assembly with one root, stable ordering and no symlinks/absolute paths.
- Confirm selected image roles match expected chip and slots, boot/app headers,
  configured flash parameters and actual source/build metadata.
- Acceptance: corrupt/missing/truncated/wrong-chip/wrong-size/overlap/renamed-file
  fixtures fail before publication. ZIP extraction into a clean temporary path
  passes `install.py check` with no source checkout or `.pio` directory available.

### 0.9.5 Implement the explicit Python installer

- Depends: 0.9.4; Python task, with firmware reviewer input on partition semantics.
- Implement the CLI in §4, package-first validation, explicit device/port checks,
  safe subprocess argument vectors/timeouts, version checks, confirmation and
  esptool write/verify handling. Use a transport adapter that tests can fake.
- Fail before writing on bad hashes, ambiguous ports, unsupported chip/flash/
  security state/layout or missing consent. Log the exact release/build ID and
  changed ranges without credentials or unnecessary unique hardware identifiers.
- Distinguish demonstrably blank/unprovisioned factory boards from an existing
  matching development layout and from unreadable/unknown/provisioned devices.
  Confirmed replacement permits only the first two cases; it is not a layout
  migration override. Test blank-first-install and unknown-layout refusal.
- Acceptance: dry-run/check/plan never open a port; ports/inspect never flash;
  install writes only manifest-approved ranges and reports verification failure.
  No full erase, NVS image, fuse programming or bypass flags are reachable.

### 0.9.6 Add Windows, macOS and Linux setup wrappers

- Depends: 0.9.5.
- Pin a qualified Python patch/dependency set and hashes; verify availability on
  the supported hosted runners. Use `.sh` and PowerShell wrappers around the same
  Python entry point; quote paths with spaces and fail on missing prerequisites.
- Test dependency setup in a fresh isolated environment, not a copied SDK/venv.
  Document first-install network use and correct Python invocation on each OS.
- Acceptance: Windows x86_64, Linux x86_64 and declared macOS architectures run
  help/check/plan/dry-run and fake-transport tests. Unsupported hosts get an
  actionable error; no global install, implicit admin/sudo or download-and-execute pipe.

### 0.9.7 Write the versioned prebuilt installation guide

- Depends: 0.9.5–6.
- Create `docs/release-installation.md` and package it as `INSTALL.md` with release
  ID, source, hardware class, setup, check, port, consent, write and reset steps.
- Include all prerequisite tools, battery disconnection, 32GB/recording limits,
  download-mode recovery, Python/USB troubleshooting and exact expected build-ID
  log. Preserve existing source-build instructions in `docs/installation.md`.
- Explain downloading from Releases versus PR Actions artifacts, including any
  outer artifact ZIP, selecting the intended head SHA and published retention
  limits. PR artifacts are temporary development builds, not stable Releases.
- Acceptance: a clean computer can follow the package guide without PlatformIO
  or a repository clone; all listed files/commands exist and match the bundle.
  Current bootstrap clearly says it does not record or offer device OTA.

### 0.9.8 Implement host/package/installer regression tests

- Depends: 0.9.1–7; no hardware writes.
- Test real package normalization from the baseline and synthetic variations;
  mock serial/esptool/GitHub calls at the boundary, not the validation logic.
- Cover bad hashes/layout/offsets, missing OTA data, wrong image, protected state,
  consent rejection, serial failure, spaces/unicode in paths, corrupt ZIP and
  absent network during dependency bootstrap.
- Acceptance: meaningful tests fail for confirmed defects; a real no-device
  invocation of esptool image analysis verifies packaged image headers. Native
  firmware tests and cross-build still pass after metadata changes.

### 0.9.9 Add the PR workflow and hash-named artifacts

- Depends: 0.9.8.
- Use `pull_request` with opened/reopened/synchronize/ready-for-review coverage,
  no path filter and no draft skip. Build the immutable PR head SHA, including
  fork PRs under read-only permissions. Record source validation in logs/manifest.
- Install the qualified Python/Core/package set on a supported pinned Linux
  runner; run native, package/installer tests, normal cross-build and size checks.
  Run no device upload, monitor, erase or embedded test execution on hosted CI.
- Upload the complete hash-named ZIP/report and display PR head/build identity.
  Set an explicit supported artifact retention period (initial target: 14 days)
  and describe expiry in the guide; GitHub Releases are the main install channel.
  Use stable required-check names; fork workflow approval remains a repository
  policy and is shown as pending, not bypassed with elevated PR execution.
- Acceptance: docs-only PR, draft, fork approval and new-head rerun cases follow
  policy; artifact/source hashes agree. Superseded PR runs may be cancelled per
  PR number, but latest head produces its own artifact. No tag/release credentials.

### 0.9.10 Add exact-main build and validation

- Depends: 0.9.9.
- Trigger `push` on `main` without path filters; checkout the triggering full SHA
  and rebuild/test/package from that source, even if a PR build already passed.
- Keep build permissions read-only, caches scoped to trusted main inputs, no PR
  artifact promotion and no stale `.pio`/test image reuse. Check lockfile drift.
- Acceptance: merge, squash, rebase and docs-only main updates identify the actual
  resulting main SHA. Build/test/package failure prevents the publish job.
  Manual retries target the recorded event SHA, not whatever main points to later.

### 0.9.11 Create and verify immutable Git tags

- Depends: 0.9.10; trusted publish job only, canonical repository/main push guard.
- Derive `firmware-main-<sha12>` and create the annotated tag at the full tested
  main SHA. Record version/run identity in its annotation; use the repository
  token with the minimum allowed `contents: write` permission.
- Verify the peeled remote target; on rerun reuse only an exact matching tag.
  Stop on conflicting target/collision/permission/ruleset failure. No force push,
  tag move, delete/recreate or release at an inferred branch tip.
- Acceptance: failed builds/PRs never create tags; matching retries are idempotent;
  different-target tags fail visibly. Tag publication does not trigger a second
  main workflow or depend on a token-generated tag event starting another run.

### 0.9.12 Publish the complete GitHub Release

- Depends: 0.9.11 and all main validation jobs.
- Retrieve the immutable artifact ID from this successful main run, validate its
  manifest/source/digests again, and create a draft against the verified tag.
  Upload ZIP/digest/notes/install guide/notices before marking it published.
- Use GitHub CLI with a body file or API structured parameters; verify the tag
  exists instead of letting release creation choose the current default branch.
- Publish current builds as `prerelease: true`, `latest: false`, clearly named
  prototype/main snapshots. Stable promotion needs separate product/device gates.
- Acceptance: downloaded release assets pass offline package integrity checks;
  target, filenames, manifest, build ID and release notes agree. No secrets/NVS
  identity files/private build directories appear. A GitHub source archive alone
  does not satisfy the release payload.

### 0.9.13 Handle retries, concurrency and partial publication

- Depends: 0.9.11–12.
- Do not cancel successful-main release work merely because a newer main commit
  arrives. Use per-source run groups or equivalent preservation; each accepted
  push gets an independent chance to publish. Do not use a single global pending
  concurrency group that discards intermediate pushes.
- A completed matching release is reused, never overwritten. Build timestamps
  may change bytes on rerun: inspect the existing published manifest/checksums,
  not equality to freshly rebuilt bytes, before declaring already published.
- For an unpublished draft with partial assets, verify exact source/tag and
  replace the entire draft asset set with one validated attempt; never mix builds.
  Keep the immutable tag at its source. A leftover tag/draft after upload failure
  is an explicit failed/repairable state, not a successful release.
- Acceptance: two rapid main merges, same-SHA rerun, interrupted upload and tag/
  asset conflict tests produce complete independent releases or visible failure,
  never a moved tag, half-published archive or silently skipped source.

### 0.9.14 Configure least privilege and required checks

- Depends: 0.9.9–13.
- Pin third-party actions to verified full commit SHAs; keep checkout credentials
  out of PR/build jobs. Default token scope is `contents: read`; only the trusted
  publish job gains `contents: write` and artifact-read access as required.
- No `pull_request_target` with untrusted checkout, release secrets in PRs,
  privileged `workflow_run` promotion of PR artifacts, persistent self-hosted
  runners for forks or shared writable PR-to-main executable caches.
- Record required stable check names and optional merge-queue integration; request
  repository administration only for concrete necessary rules. A blocked token/
  tag permission is reported, not bypassed using a broad personal access token.
- Acceptance: verify event/ref/repository guards, no write scope on PR jobs and
  no arbitrary workflow-dispatch input that can publish an untested branch.

### 0.9.15 Verify installed-package behavior on identified hardware

- Depends: 0.9.7/12 and a separately authorized XIAO unit/port and procedure.
- Perform package-only installation on a supported host, reset/boot, confirm
  source/build ID and test BOOT/RESET/reconnect plus controlled failure recovery.
  Keep the pack disconnected for USB and preserve/inspect any existing data.
- Acceptance: DEVICE evidence records hardware/port/host/release hashes/results.
  Until available, publish status remains prototype/HOST+BUILD and hardware
  installation unverified. This deferred DEVICE gate does not falsely block
  implementing PR CI or label a hosted-runner mock as a physical flash test.

### 0.9.16 Integrate documents and final milestone evidence

- Depends: 0.9.9–14; 0.9.15 reported independently.
- Update README, release guide, profile, validation and 0.9 ledger with commands,
  trigger/tag/name rules, supported OS/Python, artifact retrieval and known limits.
  Link installation assets from Releases and expected Actions run artifacts.
- Matching reviewers inspect exact changes, test engineer independently executes
  documented no-device checks, and lead completes the detached handoff review.
- Acceptance: required HOST/BUILD/CI publication tests below pass; unavailable
  DEVICE evidence remains explicit. No claim that Stage 1 recording or Stage 2
  signed OTA is delivered by automated bootstrap releases.

## 7. Validation and stopping conditions

| Test | Required observation |
| --- | --- |
| CI-T01 every PR | Docs-only, code and draft PRs start the same build checks; fork approval stays within GitHub policy |
| CI-T02 head hash | Two successive PR head commits produce differently named artifacts whose checkout, metadata and full source SHA match |
| CI-T03 normal image | Release contains the normal app, not an embedded test runner left in the build directory |
| CI-T04 exact main | Merge/squash/rebase main updates rebuild the actual resulting SHA; no PR ZIP is promoted |
| CI-T05 no failed release | Build/native/package failure creates no new tag or release |
| CI-T06 full layout | Real baseline normalizes IDF/PlatformIO paths and includes bootloader, partition table, initial OTA data and app at generated offsets |
| CI-T07 integrity | Missing/corrupt/wrong-chip/overlap/path-escape fixtures fail before installation or publication |
| CI-T08 no-device CLI | Check/plan/dry-run do not open a port; ports/inspect cannot write flash; fake transport proves explicit consent and fixed allowed ranges |
| CI-T09 host setup | Supported Windows/macOS/Linux clean environments run isolated dependency setup and package-only check/plan without PlatformIO |
| CI-T10 immutable tag | Existing same-target tag is reused; wrong-target tag fails; no force/update/delete path |
| CI-T11 release completeness | Downloaded published ZIP, external hash, manifest, notes and guide agree with exact main/tag/run; prototype state is visible |
| CI-T12 retries/concurrency | Rapid main commits and interrupted publish retain independent sources; published bytes remain immutable and drafts never mix attempts |
| CI-T13 permissions | PR/build token is read-only; publish credentials are unavailable to PR code and canonical-main guard rejects other sources |
| CI-T14 no hidden erase | No default full-chip erase, merged-gap NVS overwrite, eFuse write or security bypass; SD untouched |
| CI-T15 device install | Separately authorized package-only flash/boot/build-ID evidence; unavailable hardware remains UNVERIFIED |

Implementation defines concrete test commands in the profile. Existing baseline
checks remain `pio run -d firmware -e vdog_xiao_sense_proto`, size reporting and
`pio test -d firmware -e native`. New Python tests run from repository root using
the isolated pinned environment; version the command once its suite exists.
Do not add a green workflow step that skips an absent tool and calls it tested.

Distinguish implementation handoff from live rollout acceptance. Before merge,
run the real build/host/package/OS checks and fake-adapter publish failure tests;
record PR workflow evidence once the lead opens the implementation PR. Main
publication observations remain pending until an authorized merge triggers the
new workflow. Do not merge, fabricate production tags or publish dummy main
Releases merely to close an acceptance row. After that merge, verify the actual
main run, peeled tag, published assets and downloaded package; repair failures
through the normal change/review process. Mark 0.9 complete only when required
HOST/BUILD/live-CI observations pass; keep CI-T15 DEVICE status separate.

Stop/escalate on locked-package incompatibility on the selected CI host, missing
or conflicting flash metadata, firmware size overflow, tag/ruleset denial,
unavailable required installer dependency or unsupported protected device. Keep
