## Background (verified against the head)

1. **P2 — an expired upload can still return HTTP 200.** `UploadDetail`
   (`contracts/backend-v1.yaml` ~L1419–1453) binds `state` to `UploadState`
   (~L1375: `enum: [receiving, stored, expired]`), so the success schema of
   `GET /uploads/{id}` accepts a `state: expired` body. Probe: editing the
   golden `upload-get-response-200` vector in `fixture_spec.py` to
   `state: "expired"` (deadline removed), regenerating, and running the gate →
   `PASS … expected=valid`, `findings: 0 / RESULT: PASS`. interfaces.md §8
   step 5 (L234–236): inactive receiving uploads expire after 24 h and "return
   410"; the corpus already ships the valid `upload-get-response-410-expired`
   error answer. A 200 detail must therefore describe only a live (`receiving`)
   or committed (`stored`) session.
2. **P2 — promised response headers are declared optional.** The response
   Header Objects `UploadOffset` and `UploadLength`
   (`contracts/backend-v1.yaml` ~L951–967) omit `required`; OpenAPI's default
   is optional, yet `api_model.py` requires both on the HEAD 200 (L613) and
   `Upload-Offset` on the PATCH 204/409 (L637), and the Python response
   validator enforces them. The document checker's
   `required_response_headers` loop (`tools/contracts/openapi_check.py`
   ~L399–415) matches header *names* only. Probe: flipping the mandatory
   `components/headers/WwwAuthenticate.required` from `true` to `false` →
   `contract document findings: 0 / RESULT: PASS`. Same for the other required
   components: `AcceptRanges`, `ETagSha256`, `ContentLength`, `ContentRange`
   (206 only — the shared `RangeNotSatisfiable` 416 response carries **no**
   header, so nothing there depends on them) in both documents.
   `CacheControlNoStore` (device preview) is documented-optional
   (`documented_response_headers={200: ("Cache-Control",)}`, api_model L281)
   and must stay without the flag.
3. **P3 — the gate misses missing route parameters and dangling parameter
   refs.** `check_local_refs` runs only on the media schemas
   (`openapi_check.py` L102); OpenAPI documents are never scanned. The
   required-input work of rounds 9/10 walks only `required_request_headers`
   (`_check_operation` ~L511). Probes: (a) deleting
   `- $ref: '#/components/parameters/DeviceIdQuery'` from the backend
   `GET /clips/{clip_id}` parameters (~L170) → `findings: 0`; (b) pointing the
   clip range-download route's `Range` parameter (~L227) at
   `#/components/parameters/RangeMissing` → `findings: 0`; both mutations
   together in an isolated copy still passed all 439 fixtures. interfaces.md
   §9 (L249–264) pins `device_id` as the query that scopes every clip-keyed
   backend route (`GET /clips/{clip_id}?device_id=…`,
   `GET /clips/{clip_id}/files/{name}?device_id=…`,
   `DELETE /clips/{clip_id}?device_id=…`). A generated client would lose the
   disambiguator or fail to generate the range method.

## Steps

### 1. `contracts/backend-v1.yaml` — `UploadDetail` answers 200 only while live (Finding 1)

- Keep the `UploadDetail` `allOf` receiving-expiry conditional exactly as is.
- Narrow the `state` property so a 200 detail describes a live or committed
  session only — reference the shared state enum and refuse `expired` on top:

  ```yaml
  state:
    allOf:
      - $ref: '#/components/schemas/UploadState'
      - enum: [receiving, stored]
  ```

  (If a committed test pins the plain `$ref` shape of this member, an
  equivalent that keeps `check_local_refs`-visible resolution — same narrowing
  via the outer `allOf` — is acceptable; the observable rule is what must not
  change. Do not widen `UploadState` itself: `expired` still names the 410.)
- Update the schema `description`: say the 200 names only `receiving` or
  `stored` sessions and an expired session answers 410 (corpus
  `upload-get-response-410-expired`), on top of the receiving-expiry wording
  that stays.

### 2. Both documents — promised response headers carry `required: true` (Finding 2)

- `contracts/backend-v1.yaml` `components/headers`: add `required: true` to
  `AcceptRanges`, `ETagSha256`, `ContentLength`, `ContentRange`, `UploadOffset`,
  `UploadLength`. (`WwwAuthenticate` already carries it — keep.)
- `contracts/device-v1.yaml` `components/headers`: add `required: true` to
  `AcceptRanges`, `ETagSha256`, `ContentLength`, `ContentRange`.
  **Do not** flag `CacheControlNoStore` — the preview `Cache-Control` is
  documented-optional, and the gate must stay silent about it.
- `tools/contracts/openapi_check.py`, `required_response_headers` loop: after
  the existing name-presence check, resolve the header object for each declared
  (status, name) — guard like `_resolved_response` does, reusing
  `_RESOLUTION_FAILURES`: an unreadable header `$ref` is a
  `SPEC_COMPONENT_DRIFT` finding naming that header, never an exit-2 crash. A
  resolved Header Object must carry `required: True`; otherwise emit
  `SPEC_STRUCTURE_MISSING` with subject `{where} responses/{status}
  headers/{name}` and a detail that distinguishes "the spec requires this
  header in that response" (name absent, today's text) from "declared but not
  required". The `documented_response_headers` loop keeps its presence-only
  behaviour — those headers stay deliberately optional.

### 3. `api_model.py` + `openapi_check.py` — every parameter resolved, spec-pinned parameters present and required (Finding 3)

- `tools/contracts/api_model.py`: add one frozen field to `Operation`,
  `required_query_parameters: tuple[str, ...] = ()`, documented as the query
  parameters the spec requires by name; set `("device_id",)` on
  `backend.get_clip` (~L508), `backend.delete_clip` (~L523) and
  `backend.get_clip_file` (~L539). No other operation gains entries.
- `tools/contracts/openapi_check.py`, in `_check_operation`:
  - **Parameter reference integrity.** Walk `item.get("parameters", [])`.
    Every entry must resolve (via `_resolve`, guarded by
    `_RESOLUTION_FAILURES`) to a `Mapping` carrying string `name` and `in`.
    An entry whose `$ref` cannot be followed, or which resolves to a non-mapping
    or lacks `name`/`in`, is one `SPEC_COMPONENT_DRIFT` finding with subject
    `{where} parameters` (the name it *tried* to point at goes in the detail).
    An inline (non-`$ref`) parameter missing `name`/`in` is
    `SPEC_STRUCTURE_MISSING` on the same subject.
  - **Path-template parameters.** For every `{placeholder}` in
    `operation.path` (the document key was already proven to equal it), a
    resolved parameter with that `name` and `in: path` must exist and carry
    `required: True` — same three-way missing/optional/ok reporting the round-10
    `_required_request_parameter` uses; generalize that helper to take the
    location (`header`/`path`/`query`) instead of hard-coding `header`, keeping
    its fail-closed guard and the existing request-header loop's wording.
    Subject: `{where} parameters/{placeholder}`, `E.SPEC_STRUCTURE_MISSING`.
  - **Required query parameters.** Same check for each name in
    `operation.required_query_parameters` with `in: query`. Subject
    `{where} parameters/{name}`, `E.SPEC_STRUCTURE_MISSING`.
  - The unmutated documents must still produce zero contract findings: all
    six backend `DeviceIdQuery`/path components and the device path components
    already declare `required: true` — verify, don't assume; report anything
    that needs the flag added.
