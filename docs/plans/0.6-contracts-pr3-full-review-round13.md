## Background (verified against the head)

The checks live in `_check_operation` (`tools/contracts/openapi_check.py` ~L335–697),
which walks one table-bound `Operation` against its document node. Its response
resolution is **table-driven**: three loops read responses — `response_schemas`
(~L381), `required_response_headers` (~L435), `documented_response_headers` (~L482) —
and each reports an unreadable response as `E.SPEC_COMPONENT_DRIFT` at
`{where} responses/{status}` via `_resolved_response` (~L731). The one loop that
speaks for *every* response (`for status_key, node in responses.items()`, ~L409, the
round-12 duplicate-header gate) catches `_RESOLUTION_FAILURES` and silently
`continue`s, its comment assuming "an unreadable response is named by the loops above
and below" — an assumption that is **false** exactly where the table is silent:

1. **Finding 1 [P3] — dangling error-response refs pass.** An error status that is in
   neither `response_schemas` nor the required/documented header maps is resolved by
   no loop at all. Reproduced at the review: pointing backend
   `GET /clips/{clip_id}`'s `'404': $ref: '#/components/responses/NotFound'` at
   `#/components/responses/<Absent>` produces **zero** findings from both
   `check_openapi` and the full gate (`tools/validate_contracts.py`, 441 fixtures).
   Second half, same finding: an **optional** response header whose `$ref` dangles is
   also unreported, because only the *required* loop resolves header nodes
   (`_resolved_header`, ~L808) — the documented loop compares names only, and a header
   the table doesn't list at all (the `RangeNotSatisfiable` 416's `Content-Range` →
   `#/components/headers/ContentRangeUnsatisfied`, added round 12 exactly without table
   presence, shared by device `getClipFile` and the two backend download routes) is
   never read. Reproduced: dangling that shared component's `$ref` → zero findings.
2. **Finding 2 [P3] — the documents may advertise `Content-Length` on a `204`.** The
   no-body loop (~L544) refuses `content` on HEAD/`204` but says nothing about the
   header map: adding `"Content-Length": {"schema": {"type": "integer"}}` to
   `PATCH /uploads/{id}/files/{name}`'s `responses['204']['headers']` (which today
   carries only the required `Upload-Offset` `$ref`) produces zero findings, while the
   wire validator's `_rule_content_length` (`tools/contracts/api_validate.py` ~L733)
   already refuses the field itself on a 204 (`CONTENT_LENGTH_MISMATCH`, "a 204 answer
   may not carry the header at all (RFC 9110 §8.6)"). RFC 9110 §8.6/§15.3.2: a 204
   describes its result without a payload, so a document promising its length teaches
   generated clients to expect bytes the status can never carry. A `HEAD` answer *may*
   legitimately carry `Content-Length` (it reports the length the `GET` would have
   sent), so the rule is `status == 204` only — mirror the wire rule exactly.
3. **Finding 3 [P3] — required request-header lookup compares case literally.**
   `_required_request_parameter` (~L762–805) matches `resolved.get("name") == name`
   verbatim for every location. Renaming `components.parameters.UploadChecksum`'s
   `name` to `upload-checksum` — the same HTTP field per RFC 9110 §5.1, `required:
   true` intact — makes the checker report `parameters/Upload-Checksum` missing, while
   the round-12 duplicate-identity gate (~L613–626) and the wire validator already
   case-fold header names. Path, query, and cookie names must stay exact: RFC 9110
   folds field names, not URI template or query names.

## Steps

### 1. `openapi_check.py` — every response and every header node gets read (Finding 1)

In `_check_operation`, extend the existing all-responses loop (the duplicate-header
gate at ~L409) — or add one loop beside it if clearer — so that for **every**
`status_key, node` in `responses` (including `default`):

- Resolving `node` through `_resolve`/`_resolved_response`-equivalent guarded
  resolution: when it fails with `_RESOLUTION_FAILURES`, append one
  `E.SPEC_COMPONENT_DRIFT` finding at `{where} responses/{status_key}` whose detail
  names the unreadable reference (reuse `_resolved_response` so the detail text
  matches the table loops' wording: `$ref names {error}, a component member the
  document does not define` / `is {type}, not a response object`). Never raise past
  the CLI — exit 2 "validator internal error" remains the one forbidden outcome.
- When the response resolved and carries a Mapping `headers` member: resolve **each**
  declared header node (any value that is a `$ref`) through `_resolved_header`-
  equivalent guarded resolution and report an unreadable one as `E.SPEC_COMPONENT_DRIFT`
  at `{where} responses/{status_key} headers/{key}` (declared spelling as the subject)
  with the same wording family `_resolved_header` uses today. This covers headers the
  table never lists (the shared 416 `Content-Range`) and documented ones the
  documented loop only name-checks.
- **No double-reporting.** The three table loops already report the statuses/names
  they walk; collapse exact duplicates so one dangling shared component yields one
  finding per operation+status (+header), not two. The clean way: keep every loop's
  own wording, then at the end of `_check_operation` return `found` deduplicated on
  the exact `(code, location, detail)` triple. Distinct findings (different detail or
  subject) must survive untouched — the round-12 duplicate-header test still asserts
  `len(found) == 1` inside its filtered scope, and every other existing test stays
  green.

### 2. `openapi_check.py` — a `204` document may not declare `Content-Length` (Finding 2)

In the no-body loop (~L544) that already resolves each response for the HEAD/204
content ban, after the `content` check: when the (numeric) status is `204` and the
resolved response carries a Mapping `headers` member, any declared key whose
`str(key).lower()` is `"content-length"` earns one `E.SPEC_STRUCTURE_MISSING` finding
at `{where} responses/{status} headers/{key}` (declared spelling as subject) whose
detail cites RFC 9110 §8.6: a 204 describes its result without a payload, so the
document may not promise its length — the same rule `api_validate._rule_content_length`
enforces on the wire. `HEAD` answers keep their `Content-Length` (legitimate: they
report the `GET`'s would-be length); the committed device/backend 200/206 answers that
declare `ContentLength` must stay silent — verify the unmutated documents produce
zero findings.

### 3. `openapi_check.py` — required request headers fold case, everything else stays exact (Finding 3)

In `_required_request_parameter` (~L786–803): when `location == "header"`, match the
declared name case-insensitively (`resolved.get("name").lower() == name.lower()` on
`str` names); for every other location (`path`, `query`, anything else) keep today's
exact comparison. Keep the `in` comparison exact, keep the three-way `missing /
optional / ok` contract, keep "every match must be required" (an optional twin under
*any* spelling still answers `optional`), and keep the fail-closed behavior on
unreadable declarations. Update the docstring's rationale to say HTTP folds field
names (RFC 9110 §5.1) while path/query names stay URI-exact.
