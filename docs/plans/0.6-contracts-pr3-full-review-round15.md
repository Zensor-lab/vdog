## Background (self-contained)

The contract suite (`tools/contracts/`) validates two OpenAPI 3.1 documents
(`contracts/backend-v1.yaml`, `contracts/device-v1.yaml`) plus 441 golden fixtures
(90 media, 351 API) against an operation table in `tools/contracts/api_model.py`
(`DEVICE_OPERATIONS`, `BACKEND_OPERATIONS`, `ALL_OPERATIONS`). The document checker
is `tools/contracts/openapi_check.py::check_operation`; the fixture validator is
`tools/contracts/api_validate.py`; the loader with duplicate-key refusal and merge
semantics is `tools/contracts/schema_docs.py` (`load_yaml`,
`_construct_mapping_without_duplicate_keys`).

Key table semantics (`api_model.py`):

- `Operation.response_schemas` maps a status to its body schema. An error status
  (≥400) is deliberately **absent** when it carries the shared `Error` envelope;
  a refusal with its own schema (PUT /settings 409 →
  `SettingsRevisionConflictResponse`) is present.
- `Operation.error_codes` keys are the documented error set;
  `documented_statuses = success_statuses ∪ error_codes`.
- `content_types_for("response", status)` returns `{application/json}` for a
  table-listed error status on a non-HEAD operation and `frozenset()` for HEAD —
  "a HEAD refusal is still a HEAD: no content".

Key fixture-side behavior (`api_validate.py`):

- Every response fixture with `status >= 400` runs `_validate_error_vector`
  (call site api_validate.py:282-283).
- It selects `schema_name = operation.response_schemas.get(status) or "Error"`
  (api_validate.py:631): table-bound schema when present, else the shared `Error`
  envelope, and requires a `v`/`error.code`/… body (the media-type loop does NOT
  cover these statuses — it iterates only `operation.response_content_types`,
  which excludes plain error statuses). This is why the two document mutations
  above pass: the document checker's schema-binding loop (openapi_check.py:381)
  iterates only `operation.response_schemas.items()`, so an unlisted error status
  is never asked what schema it publishes.

Existing helpers (openapi_check.py): `_resolved_response` (full guarded resolution),
`_shallow_response` (one pointer hop, node refs left intact), `_resolved_response_node`,
`_json_schema_ref` (reads `content`'s first media entry's schema `$ref`), the
all-response scan loop (openapi_check.py:418) whose `else` branch shape-checks a
declared `headers` member (openapi_check.py:465 region), and the media-type loop
(openapi_check.py:624 region, driven by `_shallow_response`).

Round-14 rules that stay binding:

- No loop may let an unreadable node raise past the CLI: every malformed/dangling
  node earns a finding (exit 1), never exit 2 "validator internal error".
- An unreadable response/header is named once, by the all-response scan; sibling
  loops skip it rather than double-name.
- The shared `Error` envelope of both documents must stay identical
  (`check_shared_error_envelope`).

## Scope (five items)

### Item 1 (P3-1) — Error-status schema binding (`openapi_check.py`, `check_operation`)

For every documented error status ≥400 that is **absent** from
`operation.response_schemas` (iterate `operation.error_codes` keys; statuses
present in the table keep their existing binding comparison — this preserves the
dedicated `SettingsRevisionConflictResponse` 409):

- Resolve the response with the guarded full read (`_resolved_response`). When the
  read is unreadable, `continue` — the all-response scan owns that
  `SPEC_COMPONENT_DRIFT`.
- Read the response's `content` member. If it is present but not a mapping, that is
  Item 4's shape finding (coordinate, don't duplicate — see Item 4).
- No content and the operation is **not** HEAD → `SPEC_STRUCTURE_MISSING` at
  `{where} responses/{status}` explaining the contract answers this status with the
  shared error envelope and the document carries no body. (This is the review's
  mutation (a): bodyless getClip 404 must fail.)
- HEAD with no content → valid, no finding (bodyless HEAD refusals preserved).
- Content present (HEAD or not) → `_json_schema_ref(response, document)` must equal
  `#/components/schemas/Error`; otherwise `SPEC_STRUCTURE_MISSING` with the existing
  `binds {ref!r} instead of Error` phrasing. (Review mutation (b): 404 publishing the
  200 `StoredClip` schema must fail. A HEAD that publishes content also earns the
  pre-existing HEAD/204 loop's finding; do not remove that loop.)

Keep it one new loop (or extend the binding loop) with a comment explaining the
fixture-side `or "Error"` fallback it mirrors. Do not change the media-type loop's
`response_content_types` semantics.

### Item 2 (P3-2) — Declared `headers: null` shape (`openapi_check.py`, all-response scan)

The shape check currently runs only under `if declared_headers is not None:`, so an
explicit `headers: null` on a status with no required headers (e.g. shared
`NotFound`) is treated as omitted (review mutation: exit 0, 0 findings).

- Check **key presence** separately from the value on the shallow response: when
  `"headers" in shallow` and the value is not a `Mapping` (null, list, scalar, or a
  bare `$ref` node — keep the existing `$ref`-node handling of `headers_scannable`
  intact), emit `SPEC_STRUCTURE_MISSING` at `{where} responses/{status_key} headers`
  with `is {type(value).__name__}, not a map of declared header names` (so `None`
  for null).
- Keep **omission valid** (no member, no finding) and the empty map `{}` valid.
- In the two-hop `elif` branch (shallow carries no member because the component is a
  pure `$ref`), judge presence on the full-resolved response too: `"headers" in
  resolved_response` and not a Mapping → the same shape finding (this folds in the
  round-14 recorded escape, see Item 3).
- When the shape finding fires, still follow references as the branch does today
  (a dangling `$ref` keeps its own drift finding).

### Item 3 (recorded follow-up) — two-hop `$ref` alias chains (`openapi_check.py`)

- Media-type loop: a table-listed status pointing at a *pure-`$ref` alias component*
  currently gets a false `publishes [], the operation table carries […]` mismatch
  because `_shallow_response` stops at the alias (which carries no `content`).
  Follow the hop chain: while the hop result is a pure `$ref` node (only a `$ref`
  member), take the next guarded hop; on any hop failure keep the existing skip
  (the scan owns the drift). Then read `content` keys.
- Header shape escape: a response component that is a pure `$ref` to another
  response declaring a non-Mapping `headers` reaches the `elif` and escapes the
  shape refusal — covered by the Item 2 presence check on the full-resolved
  response; add a test for this alias shape (component → component with
  `headers: null` and no other headers) earning the shape finding.
- These shapes are grep-verified unreachable in both committed documents (round 14);
  tests must build them as mutated documents (deepcopy pattern, `test_contract_documents.py`).

### Item 4 (recorded follow-up) — scalar `content` must never crash (`openapi_check.py`)

A scalar `content` value on a listed download 206 (and on any response the loops
read) reaches CLI exit 2 with a `TypeError` today: `set(response.get("content", {}))`
in the media-type loop and `_json_schema_ref`'s read. Guard every such read:

- `content` present but not a `Mapping` → `SPEC_STRUCTURE_MISSING` at
  `{where} responses/{status} content` with `is {type(value).__name__}, not a
  media-type map` — named once per status (coordinate between the media-type loop,
  the Item 1 error loop, and `_json_schema_ref` call sites so one bad node does not
  produce three copies; prefer a small helper or a single owner per shape).
- Absent content stays "empty map" as today.
- Regression test: table-listed download 206 (getClipFile/getDerivativeFile) with
  scalar `content` → exit 1 with the named finding, never exit 2 (CLI-level test in
  the style of the round-14 206 CLI tests in `test_cli.py`).

### Item 5 (recorded follow-up) — merge operand aliasing an anchored sequence (`schema_docs.py`)

Reproduced: for

```yaml
s: &s
  - a: 1
  - b: 2
m:
  <<: *s
  k: v
```

`yaml.safe_load` returns `m == {a: 1, b: 2, k: v}`; `load_yaml` silently returns
`{k: v}`. Root cause: the `<<` value node is the anchored `SequenceNode` itself;
`loader.construct_object(node, deep=True)` hits the `constructed_objects` memo (the
anchor was registered when key `s:` constructed it shallowly) and returns the
generator-backed list **before** its pending generator appended the entries — so the
merge loop iterates an empty list. Fix in
`_construct_mapping_without_duplicate_keys` the way `BaseConstructor.flatten_mapping`
does it — at the **node** level: when the merge value node is a `SequenceNode`
(possibly reached through the alias), require each entry to be a `MappingNode`
(otherwise raise the same `yaml.constructor.ConstructorError("while constructing a
mapping", …, "expected a mapping for merging, but found …")` family so it still
surfaces as `yaml.YAMLError`/`SPEC_PARSE_FAILED`), and merge each entry by
constructing it; a `MappingNode` merge source keeps today's behavior. First-merge-
wins `setdefault` and explicit-beats-merge precedence must not change.

- Regression test next to `test_load_yaml_keeps_the_safe_loader_merge_semantics`
  (test_contract_documents.py:1309): the anchored-sequence-of-mappings merge returns
  every merged key and equals `yaml.safe_load` on the same text; the existing merge
  probes (override both orders, duplicate refusal, non-Mapping merge refusal,
  committed-document probes) stay green.
