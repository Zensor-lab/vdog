## R1 — paired-range fixtures accept the wrong response status (review finding 1, P2)

Defect (confirmed): in `tools/contracts/api_validate.py`,
`_evaluate_request_sidecar` (line ~1280) skips the `Range` header walk
unconditionally at 416, so `416` with `Range: bytes=0-31` passes against a
response declaring `Content-Range: bytes */1712`; a paired `206` passes with a
sidecar that omits `Range`; and line ~379 `if direction == "response" and
request_headers:` treats an explicitly empty (present, `{}`) sidecar as absent,
bypassing the required-header walk. Requirement: `docs/specs/interfaces.md`
§4 (~L149): single-range only, 206 answers a range request, "No Range returns
200", 416 refuses multipart/suffix (and, RFC 9110 §15.5.17, unsatisfiable
ranges), and device downloads require `X-Clip-Lease`.

Rule (all in `api_validate.py`):

1. Gate: `if direction == "response" and request_headers is not None:` — a
   present sidecar is judged even when its map is empty. Absent stays silence.
2. 416 branch: the sidecar's specifier is no longer excused wholesale. Keep the
   existing per-name skip for forms `_SINGLE_RANGE` refuses (multipart,
   suffix, hyphenless, junk) — the 416 legitimately refuses those. Add the
   response-side satisfiability rule: parse the sidecar `Range` with
   `_SINGLE_RANGE` (reversed intervals stay the request row's) and the response
   `Content-Range` with `_STAR_CONTENT_RANGE`; when both parse and the
   specifier is satisfiable against the declared total (`start < total` and
   `end is None or end < total`), report `CONTENT_RANGE_INVALID` at the sidecar
   location: a 416 that refuses bytes the file holds is a wrong refusal.
   Silence when no `bytes */<total>` is present (its own rules own that).
3. 206 branch: a paired `206` requires a `Range` — when status is 206 and
   neither the sidecar nor the historical vector-header echo carries one,
   report `CONTENT_RANGE_INVALID` ("§4's No Range returns 200 reads both ways:
   a 206 grants bytes no range request justified"). No sidecar at all keeps
   silence.

Committed vectors (device/invalid, copying the committed
`clip-file-response-416-suffix-sidecar` / `206-resume` control shapes —
response `{"Accept-Ranges":"bytes","Content-Range":"bytes */1712"}` +
RANGE_INVALID envelope for 416, the 206 grant headers of `206-resume`):

- `clip-file-response-416-in-bounds-sidecar`: sidecar `Range: bytes=0-31`
  (+ `X-Clip-Lease`, `If-Match` as in the control) against `bytes */1712` →
  exactly `[CONTENT_RANGE_INVALID]`.
- `clip-file-response-206-no-range-sidecar`: sidecar with `X-Clip-Lease` +
  `If-Match` but no `Range` → exactly `[CONTENT_RANGE_INVALID]`.
- `clip-file-response-200-empty-sidecar`: sidecar `{}` → exactly
  `[HEADER_MISSING]` naming `X-Clip-Lease`.

Unit tests: sidecar decision-table rows for each rule (reversed specifier at
416 still silent; `bytes=1712-` at 416 still silent; `bytes=1711-` at 416
fires; no-total 416 silent; 206 with echoed-only Range silent; empty sidecar
walks required headers), and keep the existing four 412/416 control vectors
valid.

## R2 — a frame index entry can contain two JPEGs and still pass (finding 2, P2)

Defect (confirmed): `_jpeg_violations` (`media_validate.py` ~L603) checks
`startswith(SOI)`/`endswith(EOI)` + Pillow decode + SOF agreement; a slice of
two concatenated JPEGs passes (decoder reads only the first image; the second
has no index entry or playback time). Requirement: `docs/specs/media-format.md`
§3 (~L66): `size` includes SOI and EOI, each record starts at the preceding
record's `offset + size`, the final record ends at the exact file size — one
indexed slice is one JPEG.

Rule: add a marker-chain helper to `tools/contracts/jpeg.py`, e.g.
`first_image_end_offset(data) -> int`, that walks the chain structurally like
`sof_dimensions` (fill bytes, standalone markers, variable-length segments by
length) and, in scan-data context, honours FF00 stuffing, RST `D0`-`D7`, and
returns the offset of the marker that ends the first image — the first `D9`
(EOI) — and treats a second `D8` (SOI) inside scan data as the image having
ended early (return that offset so the caller can name it; do NOT raise).
Then in `_jpeg_violations`, after the existing SOI/EOI/decode/SOF checks
(unchanged, same codes for same defects), report the new append-only code
`JPEG_TRAILING_DATA` (errors.py, `# jpeg` section) when the first image does
not end at the slice end: `first_image_end_offset(frame) + 2 != len(frame)`,
detail naming the offending offset. A slice that ends at its first EOI is
silent.

Committed vector: `media/invalid/double-jpeg-record` — one record whose slice
is two complete distinct-seed generated JPEGs concatenated, with `size` = both
lengths, real `crc32` over the concatenated bytes, contiguous offsets and file
hashes refreshed so every other check passes → exactly `[JPEG_TRAILING_DATA]`.
Unit tests: single JPEG silent; concatenated pair fires with correct offset;
trailing garbage after EOI fires; RST-padded scan still silent.

## R3 — recovered clips can declare an incorrect playback end (finding 3, P2)

Defect (confirmed): `_validate_manifest` (`media_validate.py` ~L748) only
checks `duration_us > final t_us` and the 120 s ceiling, so the recovered
fixture's `133334 → 1133334` passes. Requirement: `docs/specs/media-format.md`
§4 (~L109): "After recovery, use last frame time plus one nominal frame period,
clamped to the maximum duration".

Rule: in `_validate_manifest`, after the existing duration checks and using
the already-validated `records` (the check runs after the full index walk;
skip when `records` empty or any gate value is not `_is_int`), when
`record.get("recovered") is True`: `period_us = -(-1_000_000 //
nominal_fps)` from `profile.nominal_fps`, `expected = min(records[-1]["t_us"] +
period_us, MAX_SEGMENT_DURATION_US)`, and `duration_us != expected` → the new
append-only code `DURATION_RECOVERED_MISMATCH` (errors.py, beside the other
two `DURATION_*` codes) with a detail naming both values. Non-recovered
manifests are untouched (their measured close time is not derivable from the
index). This is consistent with the generator's own `NOMINAL_FRAME_PERIOD_US`
(ceil of 1e6/15 = 66667) and the committed `recovered-prefix` `133334`.

Committed vector: `media/invalid/recovered-duration-mismatch` — the
`recovered-prefix` plan with `duration_us = 1_133_334` → exactly
`[DURATION_RECOVERED_MISMATCH]`. Unit tests: the exact value passes; each
off-by-one direction fires; the clamp branch (final `t_us` near 120 s, expected
`120_000_000`) passes at the clamp and fires at `final + period`; a
non-recovered manifest keeps only the two existing checks.

### What each ruling changed

- **R1** — `tools/contracts/api_validate.py`. The sidecar gate is now
  `direction == "response" and request_headers is not None` (L381): a present-but-
  empty sidecar is a request and is judged as one; an absent sidecar stays silent.
  Inside `_evaluate_request_sidecar` (L1227) the 416 excuses its own `Range` only
  when `_SINGLE_RANGE` fails or the interval is reversed (L1301-1316); an ordered,
  supported specifier is kept in `ordered_specifier` and a 416 whose
  `Content-Range: bytes */<total>` proves that specifier satisfiable reports
  `CONTENT_RANGE_INVALID` at `<id>: request sidecar: Range` (L1346-1366). A 206
  whose sidecar names no `Range` and which does not echo one itself is refused
  (L1368-1382). The asymmetry the review noted is documented on the `HEADER_RULES`
  `Range` row: a 416 owes no `Content-Range` this contract requires, so with no
  `*/<total>` to read, the satisfiability rule has nothing to compare against and
  stays silent, leaving the specifier to the request row alone.
- **R2** — `tools/contracts/jpeg.py` gains `first_image_end_offset` (L138), a
  structural walk of the marker chain that returns the offset of the `FF` starting
  the first image's EOI: fill bytes, standalone markers (`00`, `D0`-`D7`, and `01`
  in a header), segments read by length, then scan data where `FF00` is a stuffed
  byte, `D0`-`D7` restarts, and `C4`/`CC`/`DC`/`DA` are the segments a scan may be
  interrupted by (`_IN_SCAN_MARKER_CODES`, L44 — `01` is deliberately *not* in that
  set: un-stuffed inside entropy data it is a byte, not TEM). A second SOI returns
  that marker's offset instead of raising. `_jpeg_violations` (L609) reports
  `JPEG_TRAILING_DATA` when `first_end + 2 != len(frame)` (L665-673) and keeps
  `JPEG_DECODE_FAILED`, with a detail beginning `marker chain to EOI:`, for a chain
  the walk cannot finish (L652-664) — see Deviations.
- **R3** — `tools/contracts/media_validate.py` `_validate_manifest` (L762) adds the
  §4 close-time equality (L800-840): when `recovered` is `True`, records exist,
  `duration_us`/`fps`/final `t_us` are ints, `1 ≤ fps ≤ 30`, `profile` is a mapping,
  the walk did not stop, and the manifest's own `frame_count` agrees with the walked
  index, `duration_us` must equal
  `min(final_t_us + ceil(1e6/fps), MAX_SEGMENT_DURATION_US)` or
  `DURATION_RECOVERED_MISMATCH` is reported at `manifest.duration_us`. "The walk did
  not stop" is handed down by the caller as `walk_stopped=walk.stopped`, because a
  prefix can be exactly as long as `frame_count`; the final-`t_us` rule above it
  reads the same last frame and is kept quiet the same way.
- **R4** — `tools/contracts/validate.py` `clip_dimensions` (L316) keys the map by
  `(device_id, clip_id)` and indexes nothing when either is not a `str`;
  `api_validate.validate_derivative_crop` (L1672) looks the cited pair up, silent
  when the citation is not a pair of strings.
