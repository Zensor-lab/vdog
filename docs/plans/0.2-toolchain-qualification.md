## 4. Exact scope (writable paths) and non-goals

Writable (all new unless listed):

1. `firmware/` — the minimal qualified PlatformIO project:
   - `firmware/platformio.ini` — `[env:vdog_xiao_sense_proto]` (platform pinned
     `platformio/espressif32@8.0.0`, board `seeed_xiao_esp32s3`, framework
     `espidf`, explicit partition table file, monitor_speed 115200) and
     `[env:native]` (host test environment). No other firmware envs.
   - `firmware/CMakeLists.txt`, `firmware/src/` (minimal `app_main` that logs a
     vdog version string built from a portable core module; no
     camera/SD/network/radio init), `firmware/idf_component.yml` pinning
     `espressif/esp32-camera` to one exact version so the camera driver is a
     real compiled dependency (link-level qualification only; no runtime use).
   - `firmware/sdkconfig.defaults` — explicit pinned-SDK options for: 8MB
     flash size, octal-mode PSRAM enable, native-USB console (USB CDC),
     custom partition table selection, and anything the toolchain needs to
     fail loudly rather than inherit silent defaults. Use the actual Kconfig
     names of the pinned framework release and record resolved values in the
     matrix.
   - `firmware/partitions/vdog_8mb_two_ota.csv` — NVS + OTA data + **two
     equal signed app slots** + reserved headroom inside 8MB, derived from
     measured minimal-image sizes with explicit margin (document arithmetic;
     do not copy Arduino `default_8MB.csv` or any 4MB/N16R8/Plus layout).
   - `firmware/test/` — `native` env host tests exercising the portable core
     module (at least one meaningful assertion path per behavior; no empty
     suite). Portable core lives in `firmware/core/` (pure C, no IDF headers)
     and is shared by both envs.
2. `docs/toolchain.md` (new) — the **version/lockfile matrix** (see §6).
3. `docs/platformio-support.md` — update §4 (and status header) to record the

## 8. Observable acceptance criteria (verdict per item in handoff)

1. Clean minimal cross-build of `vdog_xiao_sense_proto` succeeds from a clean
   checkout with pinned platform 8.0.0 (or a documented, justified official
   alternative after a recorded failure — never Arduino/fork).
2. ESP-IDF flash=8MB, PSRAM octal, and USB-console options set explicitly in
   tracked `sdkconfig.defaults` and verified in build output; Arduino-scope
   manifest settings not relied upon.
3. Custom 8MB two-slot partition table tracked, with documented size budget
   arithmetic and measured image fitting each slot with margin.
4. `esp32-camera` pinned to an exact version and compiled as a real
   dependency; no runtime camera/SD/network behavior claimed.
5. `native` environment exists, runs real tests that pass; portable core
   shared by both envs.
6. `docs/toolchain.md` matrix complete per §6 including deferred
   Flutter/Dart/OS/Rust section with honest UNVERIFIED markers.
7. Docs updates per §4 made; `git diff --check` clean; esp32-reviewer verdict
   recorded (approve / approve with notes / changes requested → fixed →
   re-reviewed).

## 9. Stop / escalation conditions (report, do not improvise)

- Platform 8.0.0 (or replacement) cannot produce a clean cross-build with
  explicit config: capture full logs, stop the build work, report the
  compatibility failure and the exact failing component/version — scope
  changes (framework/fork/board) belong to the Orchestrator.
- Registry/package download failure that outlives one retry: report blocked
  with the URL and error; vendoring upstream component sources at a recorded
  tag/SHA is acceptable for `esp32-camera` only if the component manager
  fails, with the substitution documented in the matrix.
- Any conflict between the pinned SDK's options and this packet: pick the
  documented equivalent in the matrix rather than guessing, and flag it.
- Any need for device access, installs/upgrades, or writes outside §4: stop
  and report.
