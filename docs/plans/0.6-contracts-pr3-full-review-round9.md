## Background (verified against the head)

The defects are two validator holes and two fixture-content defects:

1. **P2 — the JPEG scan walk rejects a valid between-scan DRI (and DQT).**
   `tools/contracts/jpeg.py` `_IN_SCAN_MARKER_CODES` (L47–59) admits DHT `C4`,
   DAC `CC`, DNL `DC`, SOS `DA`, COM `FE`, APPn `E0–EF`, the stuffed byte and
   the restart range — but not DQT `DB` or DRI `DD`. Once `first_image_end_offset`
   (L202–265) has opened a scan, `FF DD` falls to the "data that merely looks
   like a marker prefix" skip (L238–240), and the walk then reads the interval
   field's bytes as scan data: a legal `FF DD 00 04 00 RR` before the second scan
   of a Pillow-decodable progressive JPEG ends with the validator mistaking an
   interval byte for EOI and reporting `JPEG_TRAILING_DATA`. T.81 §§B.2.1/B.2.4.4:
   DQT and DRI are legal between-scan segments read by their length field. The
   same constant feeds `_structural_scan_offsets` (L268–322), so one allowlist fix
   covers both walks.
2. **P2 — an upload `204` can acknowledge a chunk without advancing the offset.**
   The reviewer paired the committed 512-byte `upload-patch-request-valid` headers
   (`Upload-Offset: 0`, checksum, `Content-Length: 512`) as a `.request.headers.json`
   sidecar under a `backend.patch_upload_file` `204` response whose `Upload-Offset`
   is also `0`, and the validator reported no findings. `interfaces.md` §8 step 2
   (L220–225) requires `204` + *new* `Upload-Offset` after appending; a client
   following the stale acknowledgement resends committed bytes. `_evaluate_request_sidecar`
   (`api_validate.py` L1227, called only when a sidecar is present, L381–390) has no
   upload-pair rule. `backend.patch_upload_file` requires request
   `Upload-Offset`/`Upload-Checksum`/`Content-Length` and response `Upload-Offset`
   on 204/409 (`api_model.py` L636–637), so when a sidecar is present and its two
   arithmetic headers are parseable, the response offset has exactly one legal value.
3. **P3 — a paired `416` passes when the request carries no `Range`.** Deleting
   `Range` from the committed `clip-file-response-416-beyond-eof-sidecar` sidecar
   leaves a passing `416`: the request then asks for the whole file, and a whole-file
   request can never end in `416` (RFC 9110 §15.5.17 refuses *a range*; §4's
   "No Range returns 200" reads both ways). The existing sidecar check only
   condemns a *206* whose pair names no `Range` (`api_validate.py` L1372–1391);
   `416` was left out.
4. **P3 — the baseline golden transcode changes the source aspect ratio.**
   `derivative-response-200` (drv-1, `fixture_spec.py` ~L4901–4932) cites the
   committed 64×64 baseline yet declares `output 64×36` from a `crop 64×36`
   (y=14): it preserves the *crop's* 16:9, while `docs/specs/backend.md` §7.3
   (L305–311) requires a transcode to "preserve the source aspect ratio, avoid
   upscaling". `clip-detail-response-200` (~L3740–3762) inlines drv-1's summary
   with the same `output 64×36` and must stay consistent. One more valid
   transcode has the same shape: `derivative-response-200-crop-integral-float-notation`
   (~L5044–5080, valid, cites the baseline, float-spelled `crop 64×36` at y=14) —
   a corpus-wide ratio test catches it too. The `crop-out-of-bounds*` and
   `bad-hash` 64×36 records are `expected="invalid"` (rejected on bounds/schema)
   and stay untouched; `derivative-response-200-wide-second-device` (drv-7,
   64×64 from the 128×128 capture) is already square.

## Scope

### 1. `tools/contracts/jpeg.py` — DQT/DRI between scans (Finding 1)

- Add `0xDB` (DQT) and `0xDD` (DRI) to `_IN_SCAN_MARKER_CODES`; extend the
  block comment and the `first_image_end_offset`/`_structural_scan_offsets`
  docstrings to name DQT and DRI among the between-scan segments read by
  length (T.81 §§B.2.1/B.2.4.4). No other walk logic changes — the generic
  segment-by-length path already consumes any allowlisted code.
- `make_progressive_jpeg` (L120–156) currently inserts seed-derived COM segments
  between the two SOS markers. Add deterministic DRI insertion so the corpus can
  carry a valid DRI fixture: insert exactly one `FF DD 00 04 <2-byte interval>`
  before the second SOS (seed-derived interval, kept small, e.g. 4). Keep the
  existing COM behaviour for the existing fixture; the new synthesis must still
  end at its first EOI (the function already asserts that).
- New committed fixture `media/valid/progressive-dri-between-scans` in
  `fixture_spec.py` (follow `media/valid/progressive-comment-between-scans`
  ~L360–378): same clip shape, frames encode through the DRI synthesis, expected
  `valid`. It must decode in Pillow at the manifest dimensions and pass the
  corpus gate.

### 2. `tools/contracts/api_validate.py` + `errors.py` — stale-offset upload
acknowledgement (Finding 2)

- Register a new append-only code `UPLOAD_OFFSET_STALE` in `tools/contracts/errors.py`
  next to `UPLOAD_OFFSET_INVALID` (L152) and its CODES list (~L276).
- In `_evaluate_request_sidecar`, when the operation is `backend.patch_upload_file`,
  the status is `204`, and the sidecar carries parseable nonnegative integer
  `Upload-Offset` and `Content-Length` values: require the response `Upload-Offset`
  to be a parseable integer equal to `request_offset + content_length`; otherwise
  `UPLOAD_OFFSET_STALE` at the sidecar location. Do not double-flag: when the
  sidecar's offset/checksum/length are absent or malformed, the required-header
  walk and `_rule_upload_offset`/`_rule_upload_length` already own the defect, so
  skip the pair check then; when the response offset is absent, `HEADER_MISSING`
  owns it; when it is malformed, `UPLOAD_OFFSET_INVALID` owns it — skip the pair
  check in both cases. `409` pairs are untouched: there the response offset is the
  authoritative committed offset and legitimately differs.
- Fixtures (`fixture_spec.py`, upload section ~L4247–4280):
  - `upload-patch-response-204` gains a `request_headers` sidecar mirroring the
    committed request (`Upload-Offset: "0"`, `Upload-Checksum: "sha256
    {media.baseline_chunk_sha256}"`, `Content-Length: str(media.baseline_chunk_bytes)`)
    while its response keeps `Upload-Offset: str(media.baseline_chunk_bytes)` —
    the correct 512 pair.
  - New `upload-patch-response-204-stale-offset` (category `upload`,
    `expected="invalid"`, `codes=(UPLOAD_OFFSET_STALE,)`): the same sidecar,
    response `Upload-Offset: "0"` — the exact reviewer reproduction.

### 3. `tools/contracts/api_validate.py` — `Range` required on a paired 416
(Finding 3)

- Widen the 206-only check (L1372–1391) to `status in (206, 416)`, reusing
  `CONTENT_RANGE_INVALID`; adapt the comment and message to cover both the grant
  that no range justified and the refusal of a range no request asked for (RFC
  9110 §15.5.17; interfaces.md §4 "No Range returns 200" reads both ways). Keep
  `specifier is None` semantics: a sidecar whose `Range` is present but in an
  unsupported form (`bytes=-100`, multi-range, `bytes=10`, reversed) still passes
  the pair check and the honest `416` refusals stay valid — verify the four
  committed 416-with-sidecar vectors (suffix, beyond-eof, in-bounds, clipped-end)
  all carry `Range` in the sidecar and keep their declared expectations.
  Sidecar-less vectors keep their silence (the function never runs for them).
