## 4. Part A — desk work (start immediately; BUILD/HOST evidence only)

A1. **Portable memory interface** — new `firmware/core/vdog_mem.{h,c}`
(pure C11, no ESP-IDF headers, `extern "C"` guard, same conventions as
`vdog_board.{h,c}`; consumed by `native` via `lib_deps ./core` and by the
target through the existing `components/vdog_board` wrapper or a sibling
component):
- `vdog_mem_detected_t`: flash size/mode/freq + PSRAM size/mode/speed with a
  per-field explicitly-set bitmask (missing ≠ zero, same discipline as
  `vdog_board_profile_t`) **and a per-field source tag (lead finding 2 —
  evidence honesty): `MEASURED` vs `CONFIGURED`**. Measured at runtime:
  flash chip size (JEDEC ID via `esp_flash_get_size`) and PSRAM init success
  + size (`esp_psram_get_size` after init). CONFIGURED: flash mode/frequency
  and PSRAM octal-mode/speed come from sdkconfig and only prove the image
  was built that way — the octal-mode match is shown only indirectly, by
  PSRAM initializing at all. `vdog_mem_format_detected` renders the source
  per field (e.g. `flash_size=8MB[measured] flash_mode=qio[configured]
  psram=8MB[measured:init-ok] psram_mode=opi[configured]`) and is **never**
  allowed to print "detected OPI" from config alone (host-pinned);
  `docs/hardware-identity.md` rows carry the same tags.
- `vdog_mem_check_baseline(const vdog_mem_detected_t *)` comparing against
  the documented XIAO ESP32S3 Sense build baseline (8 MiB flash QIO/80 MHz,
  8 MiB **octal/OPI** PSRAM 80 MHz): `VDOG_OK` or specific codes with
  `vdog_mem_error_field()` — and named rejects for the wrong-board classes
  the acceptance calls out (quad-only PSRAM, 4 MiB flash, no-PSRAM,
  Plus/N16R8-shaped reports). Baseline comparison checks MEASURED fields
  against expected measured values and CONFIGURED fields against the build's
  own sdkconfig; a CONFIGURED field never satisfies a "detected" claim.
- `vdog_mem_format_detected(char *buf, size_t)` — report string with
  `vdog_format_version` buffer semantics (NULL/size rules; unspecified on
  error), including the per-field source tags above.
A2. **Recovery/identity interface (portable logic)** — new
`firmware/core/vdog_recovery.{h,c}`:
- boot-mode enum + `vdog_recovery_classify(const char *rom_line)` mapping the
  ROM/EDL lines the 1.2 drill will print (USB-JTAG/serial boot, download
  mode, normal boot) to states; unknown → UNKNOWN, never guessed.
- `vdog_identity_format(vdog_identity_t*, char *buf, size_t)` composing the
  **sanitized** identity line: chip model/revision + configured flash/PSRAM
  summary + `mac_redacted` = only the OUI-independent tail (last 2 bytes
  hex) — never full MAC, never eFuse raw values, no serial numbers beyond a
  caller-supplied opaque board tag. NULL/size semantics as above.
A2b. **Portable strap/reserved-pin table (lead finding 1a)** — new
`firmware/core/vdog_straps.{h,c}` (pure C11, host-tested, same conventions):
a const table of ESP32-S3 strap/reserved pins — GPIO0 (BOOT), GPIO3, GPIO45,
GPIO46, and the native-USB pair GPIO19/GPIO20 — each with role + required
state, plus the camera/SD **candidate** pins marked `PROVISIONAL` (mirroring
`hardware/prototype-a/pin-map.csv`; the GPIO21 SD-CS/user-LED sharing stays
**unclaimed** and unresolved — no row claims it). API:
`vdog_straps_check_claim(uint8_t gpio, uint32_t claim_mask)` — a claim on a
strap pin or GPIO19/20 returns a specific error naming pin + role; candidate
camera/SD claims return the PROVISIONAL marker, never approval. All Part A
code (incl. `main.c`) claims **no** pin; host tests pin every table row and
every reject path — this is the desk half of "no strap conflicts".
A3. **IDF adapters + main.c** — `components/vdog_board` (or new
`components/vdog_board_hw/`): `vdog_mem_detected_from_sdkconfig()` (sets the
CONFIGURED source tags; #ifdef discipline like 1.1), `vdog_mem_read_detected()`
wrapping `esp_chip_info`/`esp_psram_get_size`/`esp_flash_get_size` (sets the
MEASURED source tags; compiled, executed only in Part B),
`vdog_identity_read_esp()` using eFuse **public summary only** via helper
APIs (no raw reads). `main.c` gains one `vdog_mem_format_detected` + one
`vdog_identity_format` log line after the 1.1 board line. No peripheral/strap
writes; `vdog_straps_check_claim` is the gate any future claim must pass and
today nothing claims anything; **no microphone initialization**; GPIO21 stays
untouched/unclaimed (SD-CS/user-LED sharing unresolved).
A4. **Host tests (native Unity only — no Python framework in `firmware/`)** —
new `test_vdog_mem` + `test_vdog_recovery` + `test_vdog_straps` suites:
baseline pass; each named reject (quad-only PSRAM, 4 MiB flash, no PSRAM,

Steps (each recorded; **only what actually ran is reported as DEVICE**):

   port, and **re-identify the port after every BOOT/reset transition**
   (native USB re-enumerates — finding 6).
2. Build at the Part-B tip and extract the **authoritative upload image set
   and offsets — the PlatformIO build's ACTUAL images** (verified at the
   Part A tip; review M-E): `bootloader.bin`@0x0, `partitions.bin`@0x8000,

   IDF-convention `boot_app0.bin` is NOT produced in this build) and

   the flashed files — treat it as the offset manifest only (NOT
   "app-image only", lead finding 3). Cross-check against
   `firmware/partitions/vdog_8mb_two_ota.csv`
   (nvs 0x9000–0xEFFF, otadata 0xF000–0x10FFF, phy_init 0x11000–0x11FFF,
   app0 0x20000, app1 0x320000): show that **no written image overlaps nvs
   or phy_init**; a `flash_args`-vs-CSV overlap is a **BLOCKING escalation —
   do not flash, report instead**. Record the actual esptool command line
   (from PlatformIO's verbose upload) in the bench record. Then upload:
   `pio run -d firmware -e vdog_xiao_sense_proto -t upload --upload-port
   <recorded path>`. Writing otadata resets the OTA slot choice — fine on
   this prototype, but state it in the record. Still: no `erase-flash`, no
   eFuse, no NVS content writes.
3. `pio device monitor` boot capture: verify the `vdog_mem_format_detected`
   line matches BOTH the build baseline (8 MiB flash QIO/80M configured;
   8 MiB PSRAM measured-initialized, OPI configured) AND the photographed
   revision (not Plus/N16R8/classic), with source tags rendered honestly

4. **Strap/reset evidence (lead finding 1b)**: record the ROM line's
   `boot:0x..` strapping value and the reset reason from the capture and
   compare against expected normal-boot values (and download-mode values in

   brownout/reset loop) and no mic initialization. (Reset-cause recording

package (1.3 or Part B resumption).
