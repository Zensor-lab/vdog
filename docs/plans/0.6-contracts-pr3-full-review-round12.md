## Background (verified against the head)

1. **P2 — `Content-Range` is modelled on the wrong responses.** Both documents
   publish one `components/headers/ContentRange` (device ~L682, backend ~L947) with
   `pattern: '^bytes ([0-9]+-[0-9]+|\*)/[0-9]+$'` and `required: true`, and reference
   it **only** from their `206` answers (device `getClipFile` ~L426; backend clip-file
   ~L249 and derivative ~L713). The `*/` alternative describes an *unsatisfied*
   request (RFC 9110 §14.4), and the wire validator already refuses it on a grant:
   `_rule_content_range` (`tools/contracts/api_validate.py` ~L750) fails
   `bytes */<total>` on status 200/206 with `CONTENT_RANGE_INVALID`. Meanwhile the
   shared `RangeNotSatisfiable` (`416`) response (device ~L741, backend ~L1019)
   declares **no** `headers` member, although the valid beyond-EOF fixtures legitimately
   answer `Content-Range: bytes */1712` to report the current representation length
   (`contracts/fixtures/device/valid/clip-file-response-416-beyond-eof.headers.json`
   and its `-sidecar` twin), while the hyphenless/multi-range/reversed 416 fixtures
   omit the header entirely — so on the 416 the header is legitimate **and optional**.
2. **P3 — a `204` acknowledgement can carry `Content-Length`.** `_rule_content_length`
   (`api_validate.py` ~L733) only judges the *value* (`_as_int` ≥ 0, plus the chunk
   bounds for the PATCH request), and `_body_presence` (~L450) confirms a `204` ships
   no bytes — so the golden `backend/valid/upload-patch-response-204.headers.json`
   (`{"Upload-Offset": "512"}`) stays valid when `Content-Length: 0` is added to it.
   RFC 9110 §8.6 forbids the header itself on a `204`: reject it before parsing any
   value. Request direction keeps today's value checks (the chunk PATCH requires a
   conforming `Content-Length`).
3. **P3 — duplicate declarations pass the gate.** `_required_request_parameter`
   (`openapi_check.py` ~L699–742) answers `ok` when *every* match of
   (name, in) is required, so a second required `device_id` query with an integer
   schema on `GET /clips/{clip_id}` is invisible; `_resolved_header` (~L745–771)
   `break`s at the first case-insensitive key, so a second lowercase
   `upload-offset` header (different schema) beside the required `$ref` behind
   `Upload-Offset` on `headUploadFile` 200 is never read. Both mutations in one copy
   of the head still printed `findings: 0` over all 440 fixtures. OpenAPI's Operation
   Object requires unique parameter names per location; HTTP header names are
   case-insensitive, so the two spellings are one header declared twice.

## Steps

### 1. Both documents — split `Content-Range` into the two RFC forms (Finding 1)

In **both** `contracts/device-v1.yaml` and `contracts/backend-v1.yaml`:

- Narrow `components/headers/ContentRange` to the granted form only: pattern
  `'^bytes [0-9]+-[0-9]+/[0-9]+$'`, description speaks only
  `` `bytes <first>-<last>/<total>` for the single granted range`` — drop the
  416/`*` wording. Keep `required: true` (the three 206 references keep pointing
  at it; the round-11 required-ness gate must stay satisfied).
- Add `components/headers/ContentRangeUnsatisfied`: description
  `` `bytes */<total>` on the 416 that reports the current representation length
  (RFC 9110 §14.4, §15.5.17)``, schema `type: string`, pattern
  `'^bytes \*/[0-9]+$'`, **no `required` key** — the contract permits a refusal
  without it (three valid device 416 fixtures omit the header), so OpenAPI's
  optional default is the honest spelling.
- Give each document's `components/responses/RangeNotSatisfiable` a `headers`
  member declaring exactly one optional `Content-Range` via
  `$ref: '#/components/headers/ContentRangeUnsatisfied'`. It is shared by the
  device `getClipFile` and the two backend download routes; all three 416s gain
  it together.
- Do not touch `api_model.py`. The checker's required-ness gate only speaks for
  headers the operation table demands on a status; this one is optional and
  table-free.

### 2. `api_validate.py` — `204` refuses `Content-Length` outright (Finding 2)

At the top of `_rule_content_length`: when `context.direction == "response"` and
`context.status == 204`, return a single `CONTENT_LENGTH_MISMATCH` violation on
`{location}: {name}` with a detail that says the 204 answer may not carry the
header at all (RFC 9110 §8.6), whatever its value — **before** `_as_int` runs, so
`0`, `512` and `many` are refused alike. Everything else in the rule (numeric
value, PATCH-request chunk bounds) stays. Comment the why: the separate body check
only proves no bytes are present; RFC 9110 §8.6 forbids the field itself.

### 3. `fixture_spec.py` — one new invalid vector (Finding 2 regression)

Mirror the golden `upload-patch-response-204` (~L4436): same
`request_headers` (offset 0, checksum, chunk length) and the required
`Upload-Offset: str(media.baseline_chunk_bytes)` response header, plus the single
defect `"Content-Length": "0"` on the response. `id="upload-patch-response-204-content-length"`,
`contract="backend"`, `category="upload"`, `operation="backend.patch_upload_file"`,
`direction="response"`, `status=204`, `expected="invalid"`,
`codes=(CONTENT_LENGTH_MISMATCH,)`, invariant naming AC-05 and RFC 9110 §8.6: a
204 acknowledgement never carries `Content-Length`; the `Upload-Offset` it must
keep is untouched. If the gate honestly observes a different code set, declare
what it sees (round-10/11 precedent) and say so in the handoff. Never hand-write
fixture bytes — the generator owns them.

### 4. `openapi_check.py` — duplicate declarations are findings (Finding 3)

In `_check_operation`:

- **Duplicate parameter identities.** While walking `item["parameters"]` (the
  round-11 integrity loop), collect each resolved parameter's identity: `in`
  lowercased; `name` verbatim for `path`/`query` and lowercased for `header`
  (HTTP field names are case-insensitive, path and query names are not). The
  first member of an identity is the declaration; every *additional* member is
  one `E.SPEC_STRUCTURE_MISSING` finding on `{where} parameters/{name}` (the
  resolved `name` as spelled) whose detail names the duplicated identity and how
  many members share it. Report regardless of `required` — this reads the list
  before any required interpretation — and keep `_required_request_parameter`
  exactly as round 11 left it (its optional-twin rule still applies).
- **Duplicate response-header names.** Add one loop **before** the
  `required_response_headers` loop (so the duplicate is refused before the
  required flags are interpreted): for every `status_key, node` in `responses`
  (including `default`), resolve with the same guarded `_resolve` /
  `_RESOLUTION_FAILURES` discipline used by `_resolved_response` (an unreadable
  response is named elsewhere; skip silently here); when the resolved response
  and its `headers` member are both Mappings, bucket the declared keys by
  `str(key).lower()`; each bucket with two or more spellings is one
  `E.SPEC_STRUCTURE_MISSING` finding on `{where} responses/{status_key}
  headers/{name}` (`{name}` = the first declared spelling in document order)
  whose detail lists every colliding spelling. This runs for every response,
  not only those the operation table speaks for.
- Both unmutated documents must still print zero contract findings: neither
  carries a duplicate identity or a case-colliding header today — verify, don't
  assume, and report anything that needs fixing in the documents themselves.
