## Background (verified against `c476706`)

`_check_operation` (`tools/contracts/openapi_check.py`, ~L335–720) walks one
table-bound `Operation` against its document node. Round 13 added the all-response
scan (`for status_key, node in responses.items()`, ~L418) which reads every response
and every declared header node through the guarded helpers
(`_resolved_response_node` ~L888, `_shallow_response` ~L859, `_read_header_node`
~L996) and reports `E.SPEC_COMPONENT_DRIFT` at `{where} responses/{status}` (or
`... headers/{key}`); `_check_operation` returns findings deduplicated on the exact
(code, location, detail) triple. Three gaps remain, each reproduced by the review:

1. **Finding 1 — the media-type loop is the one unguarded response read.**
   `openapi_check.py` L609–620 (`for status, types in
   operation.response_content_types.items(): response =
   _resolve(responses.get(str(status), {}), document)`) calls `_resolve` (L821)
   *directly*. `backend.get_clip_file` (`GET /clips/{clip_id}/files/{name}`,
   `contracts/backend-v1.yaml` L213+) carries 206 in `response_content_types`
   (`application/octet-stream`), so replacing the inline `'206'` response
   (`backend-v1.yaml` L243) with `{'$ref': '#/components/responses/NoSuchPartial'}`
   makes `resolve_refs` raise `KeyError` at L610; the exception discards the report
   and the CLI prints "validator internal error" with **exit 2** (cli.py L82–87).
   The scan above (L419) already resolves the same node guarded and appends the
   operation-and-status finding — the later loop simply has to reuse that guarded
   resolution and skip the media-type comparison once resolution failed.

2. **Finding 2 — a non-map `headers` member passes when it hides no broken `$ref`.**
   In the scan, `declared_headers = shallow.get("headers")` (L428): a *list* (e.g.
   `[]`) is not a Mapping, so `headers_scannable` is False (L433); `unreadable` is
   None but `"headers" in shallow`, so the code reaches the final `else` (L459) which
   only *guarded-resolves* the member (L465–483) — `resolve_refs([])` succeeds,
   `name_map = None`, `continue`: **zero findings**. Setting
   `components.responses.NotFound.headers = []` (the shared backend 404 —
   `backend-v1.yaml` L1001, which today declares no `headers` at all and is in no
   table loop) passes `check_openapi` and the full gate alike. OpenAPI's Response
   Object defines `headers` as a Map; the shape must be refused *whenever it is
   declared*, including statuses with no mandatory headers. Preserved pins the fix
   must not disturb: `headers: {"$ref": ...}` (a Mapping) stays **totally silent**
   when the ref resolves (round-13 `test_malformed_response_member_shapes_are_read_or_named`
   shape (c), pinned `assert not check_openapi(...)`); `headers: [...]` **hiding a
   dangling ref** keeps its `SPEC_COMPONENT_DRIFT` at the response (same test shape
   (b)); `headers: null` keeps its round-11 reading (read as declaring nothing —
   `test_a_null_response_headers_member_is_a_finding_not_a_crash` stays green as
   pinned).

3. **Finding 3 — `yaml.safe_load` silently keeps the last duplicate key.**
   `schema_docs.load_yaml` (L138–140) is a bare `yaml.safe_load`. Adding a second
   literal `Upload-Offset:` key ahead of the original in the backend HEAD
   (`/uploads/{id}/files/{name}`, head, `'200'` headers, `backend-v1.yaml`
   L326–328) survives loading as one key, so the round-12 duplicate-spelling gate
   (scan L497+) never sees the collision and the full validator reports zero
   findings. `validate_contracts` (`validate.py` L123–129) already catches any
   exception from `load_yaml` as an `E.SPEC_PARSE_FAILED` finding naming the file, so
   a loader that *raises* on a duplicate becomes exit 1, never exit 2. The committed
   documents contain no duplicate mapping keys (verified in the review's parse-tree
   scan), so the stricter loader keeps every committed check green.

### Fix A — loader merge semantics (`tools/contracts/schema_docs.py`)

Confirmed by both verifiers (test-engineer MEDIUM, python-reviewer LOW-2): the duplicate
guard consulted the merged `mapping` dict, so the canonical legal merge-override —
`<<: *base` whose base declares `y`, plus an explicit `y:` — raised
`ConstructorError: found duplicate key 'y'` where PyYAML yields the explicit override
(order-dependent: explicit-before-`<<` loaded). A legal future document would have died
as whole-document `SPEC_PARSE_FAILED` plus the ~600-finding cascade. The guard now tracks
the node's own **explicit** keys in a separate set and consults only that for the
duplicate check; merged keys keep `setdefault` (first merge wins among sources), explicit
keys keep direct assignment — the explicit member beats the merged one in both textual
orders, matching PyYAML. Per the test engineer's LOW: a non-Mapping merge source
(`<<: *scalar`) now raises `ConstructorError("while constructing a mapping", …, "expected
