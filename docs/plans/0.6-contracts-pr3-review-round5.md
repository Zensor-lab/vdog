### F1 — 409 `REVISION_CONFLICT` on `PUT /settings` must carry the current revision (P2)

`contracts/device-v1.yaml` L162-163 (operation description) and
`docs/specs/interfaces.md` L122-123 promise 409 "with current revision", but the
`'409'` node of `putSettings` (L185-186) refs the shared `Conflict` response,
whose closed `Error` schema (L818+: `additionalProperties: false`,
required `[v, error]`) has no revision member, and the golden fixture
`settings-put-response-409-revision-conflict` (`fixture_spec.py` ~L1535-1546)
supplies none.

Ruling R1: add an inline `'409'` response for `device.putSettings` only (do not
touch the shared `Conflict`): schema `SettingsRevisionConflictResponse`,
`type: object`, `additionalProperties: false`,
`required: [v, error, current_revision]`, `error` = `ErrorBody` mirror as in
`Error`, `current_revision` = `$ref: '#/components/schemas/UInt53'` (same
constraints as `PutSettingsResponse.revision`). Update the operation table in
`tools/contracts/api_model.py` so the ≥400 body path validates
`device.put_settings`/409 against this schema instead of `Error`.
Fixtures: update `settings-put-response-409-revision-conflict` to carry
`current_revision` (choose a value ≠ the request's `expected_revision: 4`,
e.g. 7, and say so in the invariant); add invalid vectors
`settings-put-response-409-missing-revision` and
`settings-put-response-409-revision-non-integer` (both `API_SCHEMA`).
Unit tests: the 409 body passes the new schema with `current_revision`; fails
without it; shared-`Conflict` 409s of other operations still validate against
`Error` alone.

### F2 — `401` must carry a `WWW-Authenticate: Bearer` challenge (P2)

Backend `headUploadFile` 401 (`contracts/backend-v1.yaml` ~L332-337) models a
status alone; neither contract's shared `Unauthorized` response
(device L678-685, backend L957-964) declares any header; and `HEADER_RULES`
(`api_validate.py` L983+) has no `www-authenticate` rule, so a committed fixture
carrying it would be rejected as "no documented header of this name exists".
RFC 9110 §15.5.2 requires the challenge on 401 including bodyless HEAD
responses (headers are permitted; only the body is forbidden).

Ruling R2: in both YAMLs add to `Unauthorized` a
`headers.WWW-Authenticate` node (`required: true`, `schema.type: string`,
`pattern: '^Bearer( realm="[^"]{1,100}")?$'`,
`example: 'Bearer realm="vdog"'`); extend the backend `headUploadFile` 401 node
with the same header while keeping it bodyless. `api_model.py`: every operation
with a documented 401 gains `WWW-Authenticate` in its required response headers
for status 401. `api_validate.py`: register `_rule_www_authenticate` under
`"www-authenticate"` — syntax per the pattern above, `HEADER_INVALID` on
violation. Fixtures: the generator's 401 fixtures all carry
`WWW-Authenticate: Bearer realm="vdog"` (HEAD 401s headers-only); add invalid
vectors: one API 401 missing the header (`HEADER_MISSING`), one HEAD 401 missing
it (`HEADER_MISSING`), one 401 with `Basic realm="x"` (`HEADER_INVALID`).
Update `contracts/README.md` where 401 behaviour is documented.

### F3 — a 206 may grant bytes from the wrong offset (P2)

`_rule_content_range` (`api_validate.py` L616-676) validates syntax, bounds and
`Content-Length` agreement but never against the requested interval;
`_rule_range` (L729+) judges syntax/order only. The unit table
(`tests/test_api_contract.py` ~L732: row `open-ended-206`) pins
`Range: bytes=999-` + 206 + `Content-Range: bytes 0-99/1000` as *no finding*.

Ruling R3: extend `_HeaderContext` with
`request_headers: Mapping[str, str] = field(default_factory=dict)`, sourced in
`validate_api_fixture` from an optional `request.headers.json` sidecar declared
by response vectors (new `request_headers`/`request_headers_file` fields on the
API fixture spec + generator, mirroring how `headers` works). In
`_rule_content_range`, when `context.status in (200, 206)` and the granted
(non-star) form is present and a parseable `Range` is supplied in
`context.request_headers`, verify `first == requested start` and
`last == min(requested end, total-1)` (open-ended request ⇒ expected last is
`total-1`); any mismatch → `CONTENT_RANGE_INVALID` whose detail names the
requested specifier and the granted interval. Silence when no request context
is supplied (unchanged behaviour for every existing vector).
Tests: flip `open-ended-206` to expect `{CONTENT_RANGE_INVALID}`; add rows for
matching pairs (`bytes=0-99` → `bytes 0-99/1000` silent; `bytes=900-` →
`bytes 900-999/1000` silent), `bytes=0-49` granted `0-99/1000` → violation,
and gate-status rows staying silent even on mismatch. Committed vectors:
`clip-file-response-206-wrong-offset` (request Range `bytes=999-`,
`Content-Range: bytes 0-99/1000`, `Content-Length: 100` →
`CONTENT_RANGE_INVALID`) and a valid `clip-file-response-206-resume` (request
`bytes=200-`, granted `bytes 200-999/1000`, `Content-Length: 800`).

### F7 — API IDs accept a trailing newline (P2)

Fixed-width identifiers are guarded by patterns anchored with `$` only
(`backend-v1.yaml` L1040-1091 and mirrors in both YAMLs); Python's `re` matches
`$` before a trailing newline, so `POST /devices` accepts 32 hex + `\n`.

Ruling R7: (a) add exact `minLength`+`maxLength` pairs beside the pattern on
every fixed-width string schema in both contracts — audit every
`pattern: '^…$'` declaration (device/backend DeviceId, ClipId incl. the
nullable `effective_from_clip_id` member, TokenId, Uuid, Sha256 mirrors,
timestamp) keeping each pattern untouched; (b) in `tools/contracts/*.py`,
replace trailing-`$` anchors with `\Z` in the wire-token regexes used with
`re.match`/`search` (`_CONTENT_RANGE`, `_STAR_CONTENT_RANGE`, `_SINGLE_RANGE`,
`_UPLOAD_CHECKSUM`, `_UUID`, etag/if-match, `_LOWER_HEX_32`, `_CLIP_ID`, and
any sibling with the same hole — audit them); (c) regression vector
`devices-request-id-trailing-newline` (`POST /devices` request with
`device_id` = 32 hex + `\n` → `API_SCHEMA`), complementing existing media-side
ID coverage. Unit tests: schema rejects `"<32hex>\n"` for each id schema
touched; `\n`-suffixed header values (e.g. `Upload-Checksum`) are refused.
