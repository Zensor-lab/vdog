## F1 HIGH — main lockfile drift check rejects the valid component lock

`.github/workflows/firmware-main.yml` (~line 279):
`grep -nE "^[[:space:]]*version: *(\\^|>=|~)" firmware/dependencies.lock`
matches legitimate DEPENDENCY-CONSTRAINT entries (e.g. the camera's
`version: ^1.3.1`, `'>=5.1'`, `'>=5.0'` under per-component `dependencies:`
list items) alongside resolved versions, so every `main` run fails before
publishing. `firmware/dependencies.lock` is YAML: resolved component versions
are the `version:` keys of each entry in the top-level `dependencies:`
mapping (depth-4, e.g. `version: 2.1.9`); constraints appear only inside
list items under a component's own `dependencies:` key.

Fix: parse the lock structurally (pyyaml is already in
`requirements-dev.lock`) in a new importable module
`tools/firmware/check_lockfiles.py`. Validate ONLY the resolved component
versions: every managed component entry must carry `component_hash` and an
exact `version` matching `^[0-9]+(\.[0-9]+)*([...])?$` (no range operators);
`espressif/esp32-camera` must resolve to `2.1.9`; the `idf` entry to `6.1.0`.
Dependency-constraint entries must be ignored. The workflow step calls
`python -m tools.firmware.check_lockfiles --component-lock
firmware/dependencies.lock` instead of grep.

## F2 HIGH — installer-lock parser rejects uv continuation lines

Same workflow step (~line 307) parses
`tools/firmware/installer/requirements-installer.lock` with
`re.fullmatch(r"([A-Za-z0-9._-]+)==([^\s\\]+)", line.strip())`, which fails
on real uv output (`bitstring==5.0.0 \` — trailing space + backslash
continuation). Fix in `check_lockfiles.py`: handle `name==version \`
continuation (strip the trailing ` \`), keep the existing rules (all
requirements pinned, all carry `--hash=sha256:…`, `esptool==5.4.0`), and
add the missing check that the workflow itself runs
`python -m tools.firmware.check_lockfiles --installer-lock
tools/firmware/installer/requirements-installer.lock`.

Coverage (explicit review requirement): add pytest cases that execute BOTH
checks against the actual committed lockfiles (must pass as-is), plus
negative fixtures (resolved version replaced by `^1.3.1`, missing hash,
unpinned `>=`, missing esptool pin, continuation-line variants including
multiple `--hash` lines and comment lines). This closes the gap that let
both bugs ship green.

## F3 HIGH — installer identification fails against real esptool 5.4.0

`tools/firmware/installer/install.py:51`
`CHIP_DISPLAY_RE = re.compile(r"Chip is ESP32-S3(?![0-9])", ...)` but
pinned esptool 5.4.0 prints (verified in the uv-cached 5.4.0 sdist,
`esptool/__init__.py:568-572`):
`f"{'Chip type:':<20}{esp.get_chip_description()}"` →
`Chip type:          ESP32-S3 (QFN56) (revision v0.2)` — the old `Chip is`
form never appears in v5. Real `inspect`/`install` therefore reject the
correct board.

Fix: accept both documented forms: `(?:Chip type:|Chip is)\s+ESP32-S3(?![0-9])`
(case-insensitive, whitespace-tolerant padding); `_chip_line()` must find
lines starting with `chip type:` or `chip is`. Keep ESP32-C3/other-chip
rejection. Replace the outdated mocked output with a VERSION-MATCHED
fixture: capture the exact `flash-id` output shape from the pinned 5.4.0
source (`Chip type:` padded line + `Detected flash size: 8MB` + chip_id/
manufacturer lines) for fake transport and CLI tests (`tests/support.py`
~680, `test_install_cli.py` ~496/525), not the legacy `Chip is` string.
Add a regression test asserting identification succeeds on the 5.4.0-format
fixture and fails on `Chip type:          ESP32-C3 (revision v0.4)`.

## F4 MEDIUM — reboot precedes read-back verification

`install.py` writes images with the last write using `--after hard-reset`
(transport ~833) and only then read-backs each range (~1153) — after the
board has already rebooted. Each `read_flash` reconnects
`--before default-reset --after no-reset`, so on success the board is left
stranded in the bootloader.

Fix per review direction (upstream reset behavior): write ALL manifest
ranges with `--after no-reset` (no `final` hard-reset), then verify every
range by read-back, and only after all digests match perform exactly ONE
explicit reset (`--before default-reset --after hard-reset` via a new
`transport.reset(port)`, using a harmless read-only command such as
`flash-id`/`read_mac` — confirm against the pinned 5.4.0 CLI). On
verification failure: report as today (manual power-cycle hint) and do NOT
reset. Sequence must be provable: all writes → all reads → single reset;
failure anywhere before the reset means no reset performed. Update tests:
order-assertion on the fake transport (writes→reads→reset exactly once),
failure-path test (tampered digest → nonzero exit, no reset call), plus
existing consent/no-port guarantees intact. Success log must keep saying
the device was reset only when it actually was.
