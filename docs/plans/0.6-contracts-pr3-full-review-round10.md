## Background (verified against the head)

1. **P2 — a receiving upload can omit its deadline.** `GET /uploads/{id}`
   promises the upload's current expiry (interfaces.md §8 step 5, L234–236:
   "GET `/uploads/{id}` returns state, offsets and expiry… Inactive receiving
   uploads expire after 24h"), but `UploadDetail`
   (`contracts/backend-v1.yaml` ~L1419–1437) makes `expires_at` optional and
   nullable for *every* state (`type: ['string','null']`, not in `required`).
   Omitting or nulling `expires_at` on the committed golden
   `backend/valid/upload-get-response-200` keeps the gate green. A client
   recovering after restart cannot learn its inactivity deadline.
2. **P2 — unmounted storage can report measured capacity.** `StorageStatus`
   (`contracts/device-v1.yaml` ~L1063–1086) allows numeric totals
   independently of `mounted` (`type: ['integer','null']`, minimum 0, no
   conditional). The spec (interfaces.md §4, L116–117): "Storage totals are
   zero only for measured zero, otherwise null when unmounted." Setting
   `total_bytes`/`free_bytes` on the golden `device/valid/status-response-200-unmounted`
   to zero *or* positive values still passes. Readers can mistake an
   unavailable card for an empty or full one.
3. **P3 — the OpenAPI validator misses required inputs becoming optional.**
   In an isolated checkout the reviewer marked the PATCH
   `/uploads/{id}/files/{name}` binary `requestBody` and the
   `Upload-Checksum` parameter optional; all 434 fixtures and all 61
   contract-document tests still passed. Root causes in
   `tools/contracts/openapi_check.py` `_check_operation`:
   - the `required_request_headers` loop (L502–509) delegates to
     `_declares_parameter` (L551–559), which matches only `name` and `in` —
     a parameter present-but-optional is accepted;
   - the `requestBody.required` check (L489–492) runs only inside
     `if operation.request_schema is not None:` — the chunk operation
     (`api_model.py` ~L616, `request_content_types=(BINARY_CONTENT_TYPE,)`,
     no named JSON schema) never has its `requestBody.required` examined.

## Steps

### 1. `contracts/backend-v1.yaml` — `UploadDetail` expiry required while receiving (Finding 1)

- Keep `expires_at` in `properties` with its current
  `type: ['string','null']` / `format: date-time` / `minLength`/`maxLength`
  24 / `pattern` definition so `stored`/`expired` details may carry null.
- Add a conditional so a `receiving` detail must carry a non-null `expires_at`:

  ```yaml
  allOf:
    - if:
        required: [state]
        properties:
          state:
            const: receiving
      then:
        required: [expires_at]
        properties:
          expires_at:
            type: string
  ```

- Rewrite the schema `description` (it currently *explains the optionality* as
  "names no field, so it is optional (contracts/README.md)"): say instead
  that `expires_at` is the documented 24 h inactivity deadline and a
  `receiving` detail must report it non-null; other states may omit or null it.

### 2. `contracts/device-v1.yaml` — `StorageStatus` totals null when unmounted (Finding 2)

- Keep the five numeric totals in `properties` as
  `type: ['integer','null'], minimum: 0` (measured zero stays legal while
  mounted) and add the conditional encoding of L116–117:

  ```yaml
  allOf:
    - if:
        required: [mounted]
        properties:
          mounted:
            const: false
      then:
        properties:
          total_bytes: {type: 'null'}
          free_bytes: {type: 'null'}
          rolling_bytes: {type: 'null'}
          protected_bytes: {type: 'null'}
          retained_duration_s: {type: 'null'}
  ```

  Orchestrator decision: null-enforce **all five** totals when unmounted, not
  just the two the review mutated — the golden unmounted fixture already
  nulls all five and its committed invariant reads "every total is null
  (zero means measured zero)". Do not add `additionalProperties` (responses
  stay permissive; `test_response_objects_stay_permissive` pins this).
- Extend the schema `description` to state the rule explicitly.

### Deviations from this plan, with reasons

- **Omission vector code.** Step 3 predicted `codes=(API_SCHEMA,)` for all three
  invalid vectors. `api_validate._validate_against_component` maps a
  `required`-keyword failure to `API_SCHEMA_MISSING_FIELD`
  (`api_validate.py:608`), and the corpus gate enforces declared == observed as
  set equality, so the plan's prediction would have kept the gate red; any
  existence enforcement must use `required`. The committed vector declares the
  observed `API_SCHEMA_MISSING_FIELD` (three vectors already did so at base).
- **Two extra documents.** `tools/README.md` and the stage row of
  `docs/plans/implementation-plan.md` were re-quoted too: the committed
  `test_the_docs_quote_the_actual_corpus_and_suite_counts` inspects all three, so
  touching only `contracts/README.md` would have left the suite red. Step 5
  authorises "any other file whose prose quotes 434/344/733".
- **`_resolved_request_body` helper.** Step 4 said hoist `_resolve(...)` inline.
  Inlined, an unresolvable `requestBody` `$ref` on a JSON operation would raise
  past the CLI as exit 2, which the module's own `_resolved_response` and
  `check_local_refs` exist to prevent; the helper reads such a body as empty so
  it is reported instead. Review round 1 endorsed this and asked for the wider
  exception set, which `f6c2e8d` added.
- **No sixth corpus vector** for the permissive half of the `UploadDetail` rule
  (a `stored` detail may omit `expires_at`), because Step 3 enumerates exactly
  five ids and a sixth moves every quoted count. Pinned instead by the
  document-level `test_a_stored_detail_may_still_omit_its_expiry`.
