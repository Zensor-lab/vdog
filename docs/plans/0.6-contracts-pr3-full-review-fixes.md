## Background (what the validator is)

`tools/validate_contracts.py` validates the committed contract tree: two OpenAPI
documents, the media schema set, and 393 committed golden fixtures (`contracts/fixtures/`,
index `fixtures.json`) through three check families (`media_validate.py`,
`api_validate.py`, `openapi_check.py`). API vectors carry an optional request sidecar
`<id>.request.headers.json` (read by `api_validate._load_request_headers`) describing
the request a response vector answers. The fixture corpus is generated
deterministically from `fixture_spec.py` via `generate_fixtures.py`
(`python -m tools.contracts.generate_fixtures` rewrites `contracts/fixtures`);
`test_generated_corpus_is_byte_identical_to_committed` fails on any drift, so fixture
changes are made in the spec/generator, never by hand.

Existing machinery to reuse (already correct, do not duplicate):

- `schema_docs.is_json_integer` / `decimal_is_integral` — the contract's `type: integer`
  predicate over `int`, integral `float`, and exact `Decimal`.
- `schema_docs.DRAFT202012_VALIDATOR` + `schema_error_report` — Decimal-aware schema
  reporting used by `_validate_against_component`, `_validate_error_vector`, and
  `validate_manifest_binding`.
- `media_validate._is_int` — the same predicate used by media dedicated rules.
- `media_validate.validate_manifest_fields(record, *, location_prefix)` — identity,
  close-reason and clock rules, callable with no clip or schema.
- `errors.CODES` — the stable registry; append-only (renaming/repurposing is a
  contract change).
- `ApiFixture.raw_body` — the committed exact-bytes escape hatch.
- The frame-index path `media_validate._walk_index` already parses with
  `parse_float=decimal.Decimal`; that is the "exact-number fix" to be reused.

## Scope (all in `tools/contracts/` + committed corpus + pinned docs)

### Finding 1 — apply range and precondition rules to the request sidecar

Spec source: `docs/specs/interfaces.md` §4 ("Support single … only. … No Range returns
200. Multipart/suffix ranges are rejected with 416. On resume require `If-Match` with
the original ETag; mismatch returns 412 `CONTENT_CHANGED`") and RFC 9110 §13.2.2
(preconditions evaluated before range serving). The existing decision table above
`_rule_range` already encodes this for a response's own header echo; extend the same
precedence to the sidecar map (`_load_request_headers` / `_HeaderContext.request_headers`),
which today is consulted only inside `_requested_span_mismatch`.

Rules (response vector **with** a sidecar; a vector without one keeps today's silence):

1. Judge the sidecar as a request for its operation: the required-request-header walk
   (`device.get_clip_file` → `X-Clip-Lease`) plus every `HEADER_RULES` entry in request
   direction, including the unknown-header-name refusal. Location strings must name the
   sidecar distinctly, e.g. `f"{id}: request sidecar: {name}"`.
2. Pairing on granting answers (status 200/206):
   - Sidecar `Range` present and *not* a single `bytes=start-end`/`bytes=start-`
     (suffix, multipart, hyphenless, junk) or `end < start` →
     `RANGE_MULTI_NOT_ALLOWED` (only a 416 may answer that specifier). Today
     `_requested_span_mismatch` returns `None` in exactly these cases (its
     `requested is None` early return and its `end < start` silence).
   - Sidecar `Range` present and supported, status 200 → `RANGE_MULTI_NOT_ALLOWED`:
     a Range request is answered by 206 or by a gated refusal, never a full 200
     (§4 "No Range returns 200" reads both ways).
   - Sidecar `If-Match` present, status 200/206, and the response `ETag` is missing or
     differs (strong comparison; both are quoted SHA-256 after their syntax rules) →
     new code `IF_MATCH_ETAG_DISAGREE`: the required answer is 412 `CONTENT_CHANGED`.
3. Precedence (never flag the mandated refusal of the very defect): suppress the
   sidecar `Range`-specifier findings of (2) when `status == 416`, and suppress
   `IF_MATCH_ETAG_DISAGREE` when `status == 412`. If-Match/lease *syntax* rules are
   never excused. `_requested_span_mismatch`'s existing silence for gated statuses
   (401/404/409/410 and non-grants) stays.

Fixture work (`fixture_spec.py` device section, category `range`; the generator emits
the sidecar file already via `ApiFixture.request_headers`):

- Update the golden `clip-file-response-206-resume` sidecar from `{"Range":
  "bytes=200-"}` to `{"If-Match": <payload_etag>, "Range": "bytes=200-",
  "X-Clip-Lease": <lease_id>}` (review explicitly calls out the missing pair).
- Update `clip-file-response-206-wrong-offset`'s sidecar to add `X-Clip-Lease` so its
  declared set stays exactly `CONTENT_RANGE_INVALID`.
- New valid paired vectors: 412 refusal whose sidecar `If-Match` is a different quoted
  SHA (`0`*64 vs `1`*64 style) than the clip ETag; 416 refusal whose sidecar `Range`
  is suffix `bytes=-100`. Both keep the envelope bodies the existing 412/416 vectors use.
- New invalid vectors: `206` grant answering a sidecar suffix range
  (`RANGE_MULTI_NOT_ALLOWED`); `200` full answer to a sidecar supported range
  (`RANGE_MULTI_NOT_ALLOWED`); `206` grant with sidecar `If-Match` ≠ ETag
  (`IF_MATCH_ETAG_DISAGREE`); `206` grant whose sidecar omits `X-Clip-Lease`
  (`HEADER_MISSING`).
- Do not touch the echo-header vectors (`clip-file-response-416-*`,
  `clip-file-response-412-*`, `206-multi-range` etc.): the echo path keeps its own
  table rows.

### Finding 4 — validate the upload chunk body as binary

`backend.patch_upload_file` requests are `application/octet-stream` per
`backend-v1.yaml` (1–1,048,576 bytes); today the JSON parser at `api_validate.py` ~213
rejects real bytes (`API_SCHEMA "body is not JSON"`) and the valid fixture passes with
headers alone. Treat this operation's request body as binary and never JSON-decode it
(no `v` requirement, no component schema, no control-body ceiling — the chunk bound is
the size gate below). New rule
`validate_upload_chunk_body(entry, headers, body_bytes)` (request direction only),
evaluated **after** the header walk, with size-defect precedence (a size refusal is the
finding and nothing else, matching the over-limit-record gate in `media_validate`):

- Let `declared` be `Content-Length` as int. If `body_bytes is None` (index names no
  chunk file) and `declared` is a well-formed in-range `1..MAX_CHUNK_BYTES` chunk size →
  present bytes are 0 → `CHUNK_SIZE_INVALID` alone. (Keeps `upload-patch-request-empty-body`
  (declared 0) and `-oversized-body` (declared 1048577) on their single
  `CHUNK_SIZE_INVALID`.)
- Else (bytes present): size gate `1..MAX_CHUNK_BYTES` → `CHUNK_SIZE_INVALID` alone;
  `declared != len(body_bytes)` → `CONTENT_LENGTH_MISMATCH`; `Upload-Checksum`
  well-formed (`_UPLOAD_CHECKSUM`) → compare `hashlib.sha256(body_bytes).hexdigest()`,
  mismatch → new code `CHUNK_HASH_MISMATCH`. A malformed checksum is left to
  `UPLOAD_CHECKSUM_SYNTAX` alone; an absent checksum is left to the required-header walk.

`MediaCorpus` gains `baseline_chunk: bytes` (the same `baseline.payload[:512]` the
corpus already hashes) so the generator can commit real chunk bytes; `ApiFixture`
gains a binary body form (write `<id>.chunk` raw — `_load_body` already reads any
non-headers file). Update the fixture family:

- `upload-patch-request-valid` ships the real 512-byte chunk (its headers already
  declare the exact length and hash).
- `-bad-checksum`, `-disallowed-name`, `-negative-offset` also ship the real chunk so
  their single header defect stays the only finding (their checksums already match the
  real chunk except `-bad-checksum`, whose uppercase hex keeps `UPLOAD_CHECKSUM_SYNTAX`).
- New invalid `upload-patch-request-wrong-checksum`: exact chunk bytes + well-formed
  lowercase `sha256 <64 hex>` that is not the chunk's digest → `CHUNK_HASH_MISMATCH`.
- New invalid `upload-patch-request-length-mismatch`: exact chunk bytes + in-range
  `Content-Length` off by one → `CONTENT_LENGTH_MISMATCH`.
