## Background (verified against the head)

The corpus gate (`tools/validate_contracts.py`) passes all 427 committed fixtures
with zero findings; the contract suite is green; regeneration is byte-identical.
The defects are validator holes and fixture content, not harness failures:

1. **P2 — a satisfiable range still passes with `416`.** In
   `tools/contracts/api_validate.py` `_evaluate_request_sidecar` (L1346–1367) the
   satisfiability check is `if start < file_bytes and (end is None or end <
   file_bytes)`. For the committed baseline payload (1,712 bytes) the request
   `Range: bytes=1711-1722` has `end=1722 >= 1712`, so no violation is raised and
   the 416 passes. RFC 9110 §14.1.2 makes a specified end past the representation's
   end *clamped*, not unsatisfiable: `bytes=1711-1722` on a 1,712-byte file is
   `bytes 1711-1711/1712` and the answer must be `206`. The 206 grant check already
   clamps (`_requested_span_mismatch`, L860: `expected_last = total - 1 if end is
   None else min(end, total - 1)`). The 416 check must apply the same rule.
2. **P2 — the JPEG marker walk rejects valid progressive images.** In
   `tools/contracts/jpeg.py`, `_IN_SCAN_MARKER_CODES` (L44–46) lacks COM (`0xFE`)
   and APPn (`0xE0`–`0xEF`). Once `first_image_end_offset` (L138–201) has opened a
   scan, a `FF FE`/`FF E0`–`FF EF` seen mid-scan falls to L174–176 and is skipped
   one byte, so the walk then reads the segment's *payload* as scan data:
   marker-like bytes inside a legal comment between progressive scans (e.g. an
   `FF D9` payload) are mistaken for EOI and the validator reports
   `JPEG_TRAILING_DATA` (or `JPEG_DECODE_FAILED`) on a Pillow-decodable image.
   T.81 §§B.2.1/B.2.4: COM and APPn segments are read by their length.
3. **P3 — a response header overrides an explicit request sidecar.** The paired
   206 check in `_evaluate_request_sidecar` (L1368–1384) flags a 206 only when
   *both* the sidecar `Range` and the vector's own `Range` echo are missing. The
   function is called only when a sidecar is present (`api_validate.py` L385).
   Deleting `Range` from a resume's `.request.headers.json` and adding `Range` to
   the response `.headers.json` therefore passes. The sidecar must be the source of
   truth when present. Vectors *without* a sidecar never reach this check today,
   and must keep that silence: `device/valid/clip-file-response-206` and
   `backend/valid/clip-file-response-206` commit sidecar-less 206s with no
   response-side `Range` echo and are valid — do not add a new obligation for the
   sidecar-less path.
4. **P3 — golden transcode fixtures model upscaling.** `derivative-response-200`
   (drv-1, cites the committed 64×64 baseline, L4775–4810) and
   `derivative-response-200-wide-second-device` (drv-7, cites the committed
   128×128 second-device capture, L5005–5040) both declare
   `"output": {"width": 1280, "height": 720}`. Backend spec §7.3
   (`docs/specs/backend.md` L305–311): transcode must "preserve the source aspect
   ratio, avoid upscaling". `clip-detail-response-200` (L3615–3643) inlines drv-1's
   metadata with the same 1280×720 and must stay consistent.

### 1. `tools/contracts/api_validate.py` — 416 clamp (Finding 1)

In `_evaluate_request_sidecar`, replace the L1358 condition with the clipped rule:
an ordered, supported specifier whose `start` is inside `file_bytes` is always
satisfiable (the end clamps to `file_bytes - 1`), so flag `CONTENT_RANGE_INVALID`
whenever `start < file_bytes`, whatever `end` says. Update the surrounding
L1346–1352 comment to state the clamp explicitly (RFC 9110 §14.1.2 read together
with §15.5.17). Do not change the excusal logic (`end < start`, unparseable
specifiers stay excused).

### 2. `tools/contracts/jpeg.py` — COM/APPn between scans (Finding 2)

- Add `0xFE` and `0xE0–0xEF` to `_IN_SCAN_MARKER_CODES` so an in-scan COM/APPn is
  consumed by its length field (the existing generic segment-skip path at
  L190–200); `scanning` must remain true across it (like the existing
  C4/CC/DC/DA entries). Update the constant's docstring (L36–46) to name COM and
  APPn and T.81 §§B.2.1/B.2.4.
- Add a deterministic synthesis helper (e.g. `make_progressive_jpeg`) that saves
  via Pillow with `progressive=True` and then inserts one COM segment immediately
  before every structural SOS after the first, located by a marker-chain walk
  (never a naive byte search). The COM payload must be seed-derived and embed
  marker-like bytes `FF D9` and `FF D8` so the pre-fix walk misjudges it. Inputs:
  seed string, dimensions, quality only (no clock/locale/filesystem). The helper
  must fail loudly (`raise`) if fewer than two SOS markers exist or any insertion
  point was found missing — a vacuous fixture is worse than none.

### 3. `tools/contracts/api_validate.py` — sidecar precedence (Finding 3)

In the L1368 check, when this function runs (a sidecar is present) the condition
becomes `status == 206 and specifier is None`: drop the
`_lookup_header(response_headers, "Range")` term so a response-side echo can never
excuse an explicit request that omits `Range`. Update the L1371–1375 comment: the
sidecar is the *only* statement of the question when present; the echo remains the
historical spelling for legacy vectors, which never enter this function. Leave
`_requested_span_mismatch`'s sidecar-then-echo precedence untouched (out of scope;
the review cites only the paired 206 check).
